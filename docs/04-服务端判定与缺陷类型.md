# 04 · 服务端判定与缺陷类型

> 这一篇回答：**服务端凭什么认可一条数据 —— 以及它凭什么不认可。**
>
> 说明：本版为**完整公开版** —— 相关缺陷已修复并经相关方确认，
> 因此 §7 记录的"修复前占位"口径已解除，全部细节按实际给出。
> §7 本身保留，作为一个**披露时序**的样本。

---

## 1. 判定分两层，而且它们独立

| 层 | 内容 | 拿法 |
|---|---|---|
| **规则层** | "合格线画在哪"：达标阈值、有效时段、每日次数 | 经常有接口**直接下发** —— 便宜 |
| **实算层** | "从数据算出结果"：从轨迹算是否命中、算里程、算配速 | 只能靠**实验** |

> **别因为"它有阈值"就假设"它会实算"。** 两层完全独立。

本案例的规则层是**服务端自己说的**（一个 GET 拿全）：

```text
有效时段 06:00–22:30 ｜ 达标里程 男 2.5 / 女 2.0 km ｜ 配速区间 3~10 min/km ｜ 每日有效次数 1
```

⚠️ 注意其中两项的字段名与实际语义**是反的**（字段里叫 min 的值比 max 大）。
真实语义是"配速必须落在 3~10 之间"。
⇒ **又一次"名字会撒谎"**：判据是数值的合理性（3 min/km 是人跑不出的上限），不是字段名的方向。

---

## 2. 怎么测"服务端到底算没算"

方法很朴素：**上报一个值 → 回读 → 看它变没变。**

```text
① 上报一个值（让它处在合理范围，不要离谱，否则会触发别的检查）
② 提交 → 回读
③ 逐字段比对：与上报一致 ⇒ 不重算；被改写 ⇒ 重算
```

**本案例实测（同一份响应里，"算了"与"没算"同时存在）：**

| 字段 | 上报 | 落库 | 重算？ |
|---|---|---|---|
| 里程 / 时长 / 配速 / 步数 | 2.54 / 951 / `6′14″` / 2558 | **逐字相同** | ❌ **不重算** |
| 判定结果 | —— | 服务端给出 | ✅ 有判定 |

**另一方向的证据（很关键）**：客户端上报"我打了 1 个卡"，而轨迹并不经过
⇒ **仍判不达标** ⇒ **打卡点这一项是实算的，不采信客户端上报的结论。**

> ⇒ 同一个服务端：**"数值类字段"照单全收，"结论类字段"自己算。**
>
> 这其实是**合理**的设计取向（数值是数据，结论是判断）。
> 但它直接决定了风险面在哪：数值可随便报；结论绕不过去，除非**数据本身**被操控。

## 3. 判定码表：文案没有极性，`type` 才有

服务端把判定结果以"码"下发，同时**主动**给出翻译：

```json
"reason": "11,30,40",
"reasonFormat": [
  {"type":1, "reason":"满足打卡点要求；"},
  {"type":0, "reason":"单次跑步里程 ≥ 2.5 公里；"},
  {"type":0, "reason":"单次跑步配速在 3~10 min/Km 之间；"}
]
```

| 码 | 文案 | `type` | 结论 |
|---|---|---|---|
| 10 | 满足打卡点要求 | 0 | 达标 |
| **11** | 满足打卡点要求 | **1** | **不**达标 |
| 30 | 单次跑步里程 ≥ 2.5 公里 | 0 | 达标 |
| 40 | 配速在 3~10 min/Km 之间 | 0 | 达标 |
| **41** | 配速在 3~10 min/Km 之间 | **1** | **不**达标 |

**注意 10 和 11 的文案一字不差。**

```text
码（10/11/30/40/41） = "哪一条规则"
type（0/1）          = "这条规则过没过"
status（1/2）        = 汇总：1 ⟺ 所有 type 都是 0
```

> **这一条是本项目最有迁移价值的观察之一**：
> **"翻译字段"是宝库。** 看到 `reason` + `reasonFormat`、`status` + `statusText`、
> `errorCode` + `errorMessage` 这种成对出现的东西，
> 等于服务端把内部枚举**直接交给你了** —— 比反编译客户端便宜太多。

**判据**：多条独立记录交叉、`type` 与 `status` 零冲突，**且能预测**
（只看 `reason` 就能算出 `status`）才算解出。

## 4. 三类缺陷（类型化描述）

### A. 水平越权：读他人对象

| 项 | 内容 |
|---|---|
| 形态 | 详情类接口**只认对象 id，不校验归属** |
| 判据 | ❌ 不是"响应里有没有作者字段"；✅ 是"**归属字段与我已知事实是否矛盾**" |
| 本案例 | 我的 `schoolId=5`，读到的记录 `schoolId=2` ⇒ 跨校 ⇒ 确证 |
| 影响升级 | id 为**连续自增**，且"存在/不存在"响应不同 ⇒ **可扫描出有效范围** ⇒ 从"能读一条"变成"可批量遍历" |
| 数据敏感度 | 含**完整 GPS 轨迹** / 事由文本 + 附件直链 |

**修复**：`WHERE id = :id AND owner_id = :current_user`；
并把自增 id 换成不可枚举标识 + 读取频控 + 审计。

> 为什么两条都要做：**归属校验是"这一次的补丁"，不可枚举标识是"以后所有漏判的保险"。**

### B. 数值不重算

| 项 | 内容 |
|---|---|
| 形态 | 客户端上报的统计量原样落库，服务端只做"结论类"校验 |
| 判据 | 上报特定值 → 回读 → **逐字相同** |
| 影响 | 客户端可自报任意里程/配速/步数 |

**修复**：里程由轨迹用 Haversine 累计；时长由时间戳序列校验；配速由
`duration/distance` 重算；步数与位移做一致性校验（步幅合理区间）。

### C. 数据来源未校验（本项目最严重）

| 项 | 内容 |
|---|---|
| 形态 | 提交时带一个"轨迹地址"字段，服务端**主动抓取该地址**并据此判定，**无来源校验** |
| 官方设计 | 上传要临时凭证（STS）+ 桶策略双约束 ⇒ 轨迹只能来自官方桶 |
| 实际行为 | 该字段的**来源未被校验**（指向非官方桶也被接受）⇒ 整个上传管控被架空 |
| 附带面 | 服务端主动出站请求客户端指定地址 ⇒ **SSRF 面** |
| 取证盲区 | 用地址交付轨迹时**落库为空** ⇒ 连平台自己都无法事后复核"这条记录靠什么判定" |

**修复**（优先级最高）：

1. **不接受 URL，只接受 `fileId` / 一次性令牌，由服务端自己换取对象** ——
   这样客户端**无法指定服务端去哪取数据**，来源校验从"检查字符串"变成"**结构上不可能**"；
2. 若必须保留 URL：域名白名单 + 禁止重定向 + 限制协议/端口/内网网段 + 超时与体积上限；
3. **轨迹拉到后立即在服务端本地持久化**（现在不落库 ⇒ 争议无法裁决）。

### 一条负向结论（同样入档）

教师端若干接口对**学生 token 正确拒绝**（返回 `{"code":1,"msg":"无权限…"}`）。
**这一层做对了。**

但报告里必须带备注：**本轮用的方法形态（GET）**，
因为"方法不对被拒"和"无越权"看起来一样 —— 见 `docs/03` §3。

## 5. 一个更通用的教训：防线层数多 ≠ 防线有效

项目早期的难度评估认为"服务端校验很强"（评分 ★★★★☆），理由是它确实做了：

```text
轨迹与围栏/打卡点的交叉校验、内外点数、步数与距离、历史行为……
```

**这个模型里没有一处推理错误** —— 它只是**假设了每一层防线都真的生效**。

而实际：

| 防线（设计上） | 实际上 |
|---|---|
| 轨迹只能来自官方桶 | **来源不校验**（缺陷 C）⇒ 形同不存在 |
| 打卡点随机化 ⇒ 无法预知 | 候选池有限，覆盖全池的代价**低于达标线** ⇒ 随机被消掉 |
| 步数与距离交叉验证 | **服务端不重算**（缺陷 B） |

**三条里三条都有洞 —— 但评估把它们全当成"已生效"。**

> ★ **评估难度之前，先逐层确认"这一层防线是否真的生效"。**
> 否则你估的是「**设计意图的难度**」，不是「**实现出来的难度**」——
> 而这两者之间的距离，**往往就是漏洞所在的地方**。

### 关于"随机化不能作为防伪手段"

打卡点位置每次随机下发 2 个。直觉上这像一道防线，但三条都不满足：

| 必要条件 | 打卡点位置 |
|---|---|
| 不可预知 | ❌ 池子有限、可枚举 |
| 不可复制 | ❌ 同一组点可复用 |
| **不必告诉对方** | ❌ **必须告诉** —— 不说，真人也跑不了 |

> **一个为了防作弊而必须告诉你的信息，天生不是防伪依据。**
> 它只能防"不照着点跑"，防不了"照着点跑"。

而当"覆盖全部候选"的代价**低于达标线**时，连"随机"这个属性都失效了。
（详见 `docs/05` §4 的"覆盖与代价"判据。）

## 6. 修复优先级（本案例给委托方的建议）

| 优先级 | 动作 | 对应 |
|---|---|---|
| **P0** | 详情类接口加**归属校验**；id 换不可枚举；读取加频控与审计 | A |
| **P0** | 提交接口的**来源字段改为 fileId 换取**，不接受外部 URL | C |
| **P1** | **服务端重算**统计量并做交叉一致性校验 | B |
| **P1** | 轨迹拉到后**立即本地持久化** | C 的取证盲区 |
| **P1** | 无效记录不参与排行/汇总 | B |
| P2 | 榜单最小化（脱敏）；名册分页按需；校区/围栏按校隔离 | —— |
| **加固建议** | 读取接口**限频**（正常用户一次跑步只读 1~2 次）；把"防伪"从"位置保密"转到"数据来源 + 内在一致性" | —— |

## 7. 披露时序样本：为什么"修复前"本篇用占位符

> **现状说明**：本节是**历史口径的留存**。相关缺陷已修复并经相关方确认，
> 因此 `docs/08`/`docs/09` 已给出实际路径；本节保留是为了记录"披露时序"这一决策本身。

本项目的定位是**方法论留档**，不是缺陷利用指南。

其中"能读到他人数据"和"能提交一条被认可的记录"这两类，
在厂商**修复之前**公开精确路径，会直接便利两类滥用：
对**非授权第三方**的手把手教程，以及对**未参与的第三方学生**的隐私侵害。

所以我们选择：

```text
✓ 公开：缺陷类型、判据、影响面、修复方案、判定逻辑、码表、难度评估
✗ 占位：具体可读他人数据的路径；精确到可复制的提交参数
```

**这与本仓库不提供"可用客户端"是同一条原则：知识公开，能力设门槛。**
