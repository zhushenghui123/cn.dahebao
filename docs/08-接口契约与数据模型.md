# 08 · 接口契约与数据模型

> 这一篇是**可复用度最高**的一份：把"模块有哪些接口、数据长什么样、格式契约是什么"
> 完整交代清楚。它是后面所有分析（判定还原、数据构造）的地基。
>
> > 本版为**完整公开版**：相关缺陷已修复并经相关方确认，全部路径与契约按实际给出。

## 1. 统一信封

所有接口共用一层壳：

```json
{"code":0, "msg":"OK", "time":1792154154, "data":{…}}
```

| 字段 | 含义 |
|---|---|
| `code` | 给机器判断（**注意语义混装，见 `docs/03 §2`**） |
| `msg` | 给人看（**不是根因**） |
| `time` | 服务端时间（秒） |
| `data` | 业务负载 |

`code` 的实测取值：

```text
0     成功
1     业务拒绝（如无权限）     → {"code":1,"msg":"无权限访问教师端"}
-1    未登录                  → {"code":-1,"msg":"用户未登录"}
403   方法不对                → {"code":403,"msg":"不支持的请求类型"}
500   服务端异常（缺必填参数也会 500）
```

⚠️ 但**"路由不存在"和"没登录"根本不在这套 `code` 里**：
前者走 `HTTP 404` + 网关 JSON，后者走通用拦截的纯文本。详见 `docs/03 §2`。

## 3. 数据模型（全部从真实响应推导）

```text
Student    {id, schoolId, bizType, userId, sequence(学号), name, sex, department,
            major, clazz, studentTeacherName, studentTeacher:bool}
Semester   {id, schoolId, name, start, end}
RunRecord  {id, schoolId, fenceId, start, end,
            distance(km,float), duration(秒,long), pace("m′ss″"), step,
            status, reason(逗号分隔码), reasonFormat[{reason,type}],
            ddPoints, receive, appealStatus,
            innerNum, outerNum, checkInNum, trajectory, trajectoryUrl, checkInJson,
            jpaVersion, createdDate}
ApplyFor   {id, studentId, start, end, reason, attachment, status}
Teacher    {id, schoolId, sequence(工号), name, subject, campus, week, period, selected}
RankItem   {id, schoolId, bizType, bizId, semesterId, applyForTimes, runTimes,
            distance, duration, rank, percent, name, avatar, nickname}
MyReport   {applyForTimes, runTimes, distance, duration, percent, nickname}
Points     {userId, usableScore, todayScore, aboutExpiryScore}
Page<T>    {page, size, total, data[]}
```

### 一个易混点

`RunRecord.fenceId` 是**围栏 id**，不是校区 id。
实测：同一条记录 `fenceId=1` 与另一条 `fenceId=6`，而 `fence/getList` 里 id=6 是那条
`type=2` 的镂空围栏。

## 4. 格式契约（本项目最贵的一节）

**这些只能从真实样本读出来，注解给不了。**

| 字段 | 契约 | 踩过的坑 |
|---|---|---|
| `distance` | **km**（float，下发时四舍五入 2 位；**内部计算用未舍入值**） | 用下发值反算配速会差 7 秒（`docs/03 §6`） |
| `duration` | **秒**（long） | —— |
| `pace` | 字符串 `{分}′{秒:02d}″`，用 **U+2032 / U+2033** | **不是 ASCII 引号**；用错静默不匹配 |
| `step` | 步数（int） | 必须与 `distance` 对得上（步幅合理区间） |
| `trajectory` | `[[{"longitude":…,"latitude":…}, …], …]` | **外层是段数组**；点里**只有经纬度** |
| `checkInJson` | 实测**空串**（即使 `checkInNum>0`） | 可选字段 |
| `trajectoryUrl` | 实测**空串**——说明轨迹上传不是建记录的必要条件 | ⚠️ 这正是缺陷 C 的入口 |
| `status` | 1 有效 / 2 无效 / 3 语义未知 | `3` 只观测到一次，需对方确认 |
| `reason` | 逗号分隔判定码；文案由服务端 `reasonFormat` 下发 | 文案无极性，`type` 才有（`docs/04 §3`） |

### `trajectory` 只有经纬度 —— 这一条的后果

```text
服务端能做的检查：点与点的几何、点数与里程比例、是否全点相同、是否在围栏内
服务端做不到的：  逐点时间戳序列、速度曲线是否像人、步频与轨迹是否一致
```

> ★ **这是"格式设计决定防线上限"的教科书例子。**
> 想有内在一致性检查，前提是手里有**多个可以互相约束的维度**；
> 只给经纬度，等于主动放弃一半检查能力。
>
> **给维护方的第一条建议**：要求逐点时间戳，并与步数/传感器交叉验证。

### 提交表单 13 字段（来自客户端注解，顺序即注解顺序）

```text
schoolId, fenceId, start, end, distance, duration, pace, step,
innerNum, outerNum, checkInNum, trajectoryUrl, checkInJson
```

> **注解只能给"字段名与顺序"，给不了"值该长什么样"** ——
> 后者才是真难的部分，见上表。

## 5. 怎么自己核这张表

| 想知道 | 怎么做 | 判据 |
|---|---|---|
| 端点方法对不对 | 用 GET 打一遍，看是否回 `403 不支持的请求类型` | 见 `tools/probe_endpoint_exists.py` |
| 参数要哪些 | 让官方前端/客户端跑一遍，网络层抄 | 页面渲染出真实内容 |
| 服务端算不算某字段 | 上报一个合理值 → 回读 → 逐字比对 | 变了才算它算了 |
| 格式契约 | 至少读**两条来源不同**的真实记录 | 一致的部分才是契约 |
| 判定语义 | 多条记录交叉，`type`/`status` 零冲突 | 且**能预测**才算解出 |
