## 二、核心发现

### F-01【P0】`runRecord/detail` 跨校读他人完整 GPS 轨迹

**判据不是"响应里有没有作者字段"，而是"响应记录的 `schoolId` 与我档案的 `schoolId` 是否一致"。**

| 项 | 值 |
|---|---|
| 我的档案 | `personalInfo.schoolId = 5`（河南牧业经济学院），`sequence = <学号>`（档案里的学号字段；`personalInfo.id` 是自增主键，不是学号） |
| 读到的记录 | `id=<他人A>` → `schoolId=2`；`id=<他人B>` → `schoolId=2`（河南开封科技传媒学院） |
| 泄露内容 | **完整 GPS 坐标串** + 起止时间 + 步数 + 判定原因码 + 积分 |
| 接口行为 | 只认 `id`，**不校验归属**；`id` 为**可枚举自增主键**（`id=1/2` 返回 500，说明范围可探） |

**影响**：任意学生 token ⇒ 遍历 `id` ⇒ **全校/跨校学生出行轨迹库**。GPS 轨迹属敏感个人信息，可还原宿舍—教室—作息规律。这是本次最高危发现。

**最小复现**
```http
GET /api/runRecord/detail?id=<他人B>&app_id=210710201732916889&timestamp=<ts>&token=<u_token:…>&sign=<md5>
→ {"code":0,"msg":"OK","data":{"id":<他人B>,"schoolId":2,"distance":0.35,"duration":252,
    "pace":"12′07″","step":92,"trajectory":"[[{\"latitude\":<略>,\"longitude\":<略>},…]]", …}}
```

**修复**：`runRecord/detail` 必须带上 `WHERE student_id = :当前登录学生` 或 `WHERE school_id = :当前学校`；
同时把自增 `id` 换成不可枚举标识（UUID/雪花），并对读取接口加频率限制与审计。

### F-02【P0】`applyFor/detail` 读他人请假事由与附件

- 本人 `applyFor/getList` 为 `total=0`，`studentId=<学号>`；
- 但 `id=1..6` 逐一返回**他人**记录（`studentId` 分别为 <他人 studentId，逐一略>），
  含**请假事由文本**与**附件直链**（`obs.dingxinwen.cn`）、审批状态。

**影响**：他人请假事由（可能含病因等健康信息）+ 附件可被任意学生读取。
**修复**：同 F-01，做归属校验；附件改用带时效的签名 URL 且校验请求者身份。

### F-03【P1】提交跑步记录时服务端不重算客户端自报值

**这是本模块最本质的业务逻辑缺陷。**客户端只负责采集与上报，判定权应在服务端；实测**服务端不重算**。

**写前基线**：本人 `runRecord/getList total=0`；学期进度 `myTimes=0 / myMileage=0`。

**动作**（授权范围内的一次提交，用于验证服务端是否重算）
```http
POST /api/runRecord/save
  schoolId=5&fenceId=16&start=2026-10-16 09:49:03&end=2026-10-16 10:04:54
  &distance=2.54&duration=951&pace=6′14″&step=2558
  &innerNum=191&outerNum=0&checkInNum=0&trajectoryUrl=&checkInJson=
← {"code":0,"msg":"OK","data":89740}          ← 服务端创建记录并返回 id
```
**回读 `GET /api/runRecord/detail?id=89740`**：

| 字段 | 我上报 | 服务端落库 | 是否重算 |
|---|---|---|---|
| `distance` | 2.54 | **2.54** | ❌ 未重算 |
| `duration` | 951 | **951** | ❌ 未重算 |
| `pace` | `6′14″` | **`6′14″`** | ❌ 未重算 |
| `step` | 2558 | **2558** | ❌ 未重算 |
| `innerNum` / `outerNum` | 191 / 0 | **191 / 0** | ❌ 未重算 |
| `status` | （服务端判定） | **2（无效）** | ✅ 有判定 |

**要点**
1. `trajectoryUrl` **可为空** ⇒ 轨迹上传**不是建记录的必要条件**；
2. `status=2` 的原因**不是**里程或配速 —— 是**打卡点要求未满足**（因 `trajectory` 为空）；
3. **该记录不计入学期考核**：提交后 `myTimes=0 / myMileage=0` **未变**（无效记录不计数）。

**影响**：客户端可自报任意里程/配速/步数。若配合通过"打卡点"校验，即构成完整的绕过体测链路
（**该后续步骤不在本次授权范围内，未执行，见 §五**）。

**修复建议**
1. **服务端重算**：里程由 `trajectory` 用 Haversine 累计；时长由设备时间戳序列校验；
   配速由 `duration / distance` 重算；步数与位移做一致性校验（步幅合理区间）。
2. **强制轨迹**：`trajectoryUrl` / `trajectory` 为空直接拒绝，不允许建记录。
3. **轨迹不可信**：轨迹与围栏、打卡点、时间戳序列在服务端交叉验证；
   检测"全点相同""点数与里程不成比例"（实测 `id=<他人A>` 即此形态：6143 点、0.68 km、同一点重复）。
4. **统计口径**：无效记录不应参与任何排行/汇总。

### F-07【P0】`trajectoryUrl` 无校验 —— 服务端抓取任意外部 URL，架空官方上传管控

**这是本次最严重的发现，且它把 F-08 从"理论可行"变成了"已拿到有效记录"。**

**官方设计**（从原生 dex 读出的完整链路）：
```
GET /api/upload/tos/school/token  → 对象存储的临时上传凭证
  ↓ 用 com.volcengine.tos.TOSV2 把轨迹文件 PUT 到官方桶
  ↓ 拿到 resourceUrl
POST /api/runRecord/save  with  trajectoryUrl=<官方桶 URL>
```
即：**轨迹只能来自官方桶**，凭 STS 凭证与桶策略双重约束。

**实测结论：服务端对 `trajectoryUrl` 没有任何来源校验。**

**验证方式（缺陷级描述）**

在授权范围内做了一次单发验证：构造一条轨迹，让其**来源方不是官方桶**，
提交后服务端仍然读取了该轨迹并据此完成判定，返回 `status=1`。

```text
观察到的行为：
  · 服务端未校验 trajectoryUrl 的域名/归属
  · 服务端确实读取了该地址的内容，并按轨迹判定（三项均达标）
  · 回读时该记录的历史轨迹为空 —— 服务端未将轨迹落库
```

> 具体的交付方式与可复制步骤**不在此公开**（理由见 §七）。
> 有需要的维护方可通过 Issue 联系获取。

| 回读字段 | 值 |
|---|---|
| `status` | **1（有效）** |
| `reason` / `reasonFormat` | `10,30,40` → 打卡点✅ / 里程✅ / 配速✅（三项均 `type:0`） |
| `checkInNum` | 2 |
| `distance` / `duration` / `pace` / `step` | 2.63 / 964 / `6′07″` / 2473（**原样采信，见 F-03**） |
| `trajectory`（回显） | 空 —— **服务端用 URL 交付时不回显轨迹**，但它确实读取并按轨迹判定了 |

**影响（为什么是 P0）**
1. **彻底架空上传管控**：那套 STS 凭证 + 官方桶的设计**完全无用**，因为服务端接受任何 URL；
   攻击者既不需要 App、也不需要 STS 凭证、更不需要破解 `Ck.getTDesKey()`。
2. **SSRF 面**：服务端会**主动出站请求客户端指定的任意 URL** ⇒ 可用来探测内网/云元数据/内网服务可用性，
   风险不限于跑步业务。
3. **配合 F-03**（不重算里程/配速/步数）：结合本发现即构成**完整的绕过体测链路**（本次已实测打通，产生 1 条有效记录）。

**修复建议（优先级最高）**
1. **`trajectoryUrl` 必须做来源校验**：仅接受官方桶域名（且校验对象归属当前用户/学校），其余一律拒绝；
   更稳的做法是**不接受 URL，只接受上传后的 fileId/token**，由服务端自己换取对象。
2. **服务端发起任何出站请求都应走白名单 + 禁止重定向 + 限制协议/端口/内网网段**（防 SSRF），
   并对该请求做超时与体积上限。
3. **轨迹拉到后立即重算并在服务端本地持久化**（现在用 URL 交付时 `trajectory` 落库为空，
   导致**事后无法复核**该记录是靠什么轨迹判定的 —— 这也是取证盲区）。

### F-08【P1】打卡点随机化下发**不能防绕过**（机制已完全查清）

**校方的设计**：`fence/detail` 返回 `checkInPoint = [{center:[lng,lat], radius:m}]`，
即"本次跑步必须经过这些圆"。**且判定是服务端从轨迹自己重算的，不采信客户端上报的 `checkInNum`** ——
这一层**做对了**（实测：上报 `checkInNum=1` 但轨迹不路过 ⇒ 仍判码 11；id=53/54 同）。

**更精细的事实（修正早前的笼统表述）**：随机化**不是按 `type`**，而是**按围栏配置**：

| 围栏 | 学校 | `type` | 打卡点行为 |
|---|---|---|---|
| 16 / 17 / 18 | 5（本校） | 1 | **每次请求随机变** |
| 1 / 6 | 2 | 1 / 2 | **恒定** |

**为什么它防不住（三个原因，均有实测数据）**：

1. **位置对客户端必须可知** —— 否则真人也没法跑 ⇒ 打卡点**天生不是防伪依据**，只能防"不照着点跑"。
2. **候选池有限且可枚举** —— 围栏 16 的池子**只有 10 个圆**，每次随机下发其中 **2** 个。
   **30 次 `fence/detail` 即枚举饱和**（第 20 次后不再增长），组合数仅 **C(10,2)=45**。
3. **覆盖全池的代价显著低于达标线** —— 把全部候选圆串起来的里程，**远小于单次达标所需的里程**
   ⇒ 一条合规长度的轨迹即可顺路穿过全部候选点（本地计算，多种子稳定成立）。

**两条可行路径（只给性质，不给步骤）**

| 路径 | 性质 | 依赖的假设 |
|---|---|---|
| A（已实测产生一条有效记录） | 按本次下发的那组点构造 | 服务端按"刚下发给你的那组"校验 |
| **B（更稳，已本地多种子验证）** | 覆盖整个候选池 | **不依赖任何假设**：无论校验哪 2 个都必中 |

**★ 给校方的关键结论**：**"打卡点位置随机化"不能作为防伪手段** ——
客户端必须知道点在哪才能跑，所以位置天生公开；随机化只是把"1 个固定答案"变成
"45 选 1 的小组合空间"，**30 次请求就枚举完了**。
**防线必须建在「数据来源 + 内在一致性」上，而不是「位置保密」上**：
① 修 F-07；② 服务端重算里程/配速/步数；③ 要求逐点时间戳 + 与步频/传感器一致性；
④ 打卡改成"到点现场生成不可预知内容"（照片/人脸/与时间绑定的签名）；
⑤ 若仍用打卡点，把池子做大做动态，并**限制 `fence/detail` 读取频率**（枚举全池只花了约 30 次请求）。

## 三、服务端判定码表（已完全解出）

服务端在 `runRecord/detail` 中**主动下发** `reasonFormat`，把 `reason` 的码翻译为文案。
三条真实记录交叉反推，**完全自洽**：

| 码 | 文案（固定规则描述） | `type` | 判定 |
|---|---|---|---|
| **10** | 满足打卡点要求 | `0` | ✅ 达标 |
| **11** | 满足打卡点要求 | **`1`** | ❌ **不**达标 |
| **30** | 单次跑步里程 ≥ 2.5 公里 | `0` | ✅ 达标 |
| **40** | 单次跑步配速在 3~10 min/Km 之间 | `0` | ✅ 达标 |
| **41** | 单次跑步配速在 3~10 min/Km 之间 | **`1`** | ❌ **不**达标 |

> ★ **文案是固定的规则描述，判定结果在 `type` 里。**
> `status = 1` ⟺ **所有项 `type == 0`**；存在任一 `type == 1` ⇒ `status = 2`。

| 记录 | `reason` | 各项 `type` | `status` | 自洽 |
|---|---|---|---|---|
| id=<他人B> | `10,30,40` | 0,0,0 | **1** 有效 | ✅ |
| id=89740（本次提交） | `11,30,40` | **1**,0,0 | **2** 无效 | ✅ |
| id=<他人A> | `11,30,41` | **1**,0,**1** | **2** 无效 | ✅ |

**服务端判定规则（下发值，实测）**：`/api/school/config` → 有效时段 `06:00–22:30`、每日 1 次、
`maleMileage 2.5 / femaleMileage 2.0` km、配速区间 `3~10 min/km`。

## 四、复现与环境

### 4.1 鉴权（本模块用 **H5 一套**，与原生网关那套不同）

```
GET/POST https://school-api.dingxinwen.cn/api/xxx
  ?app_id=210710201732916889 & timestamp=<秒> & token=<u_token:…> & sign=<md5>
sign = md5( 按 key 排序的 "k=v" 直接拼接（空值也计入） + web_app_secret )
```
- `token` **必须带 `u_token:` 前缀**，去掉前缀 → `{"code":-1,"msg":"用户未登录"}`；
- **GET/POST 差异**：读接口两种方法都可能（方法错 → `403 不支持的请求类型`，**不是**无权限）；
  写接口（`getList`/`save` 等）为 **POST + JSON body**（认证参数在 query）。

### 4.2 复现脚本（本目录）

```bash
python3 page_login.py         # ① 官方 H5 登录取 token（人工过滑块）→ .token(0600)
python3 policy.py             # ② 拉取判定规则 + 地理约束（单一事实源）→ policy_out.json
python3 campus_reverse.py     # ③ 23 端点全量探测 → campus_reverse_out.json
python3 h5_campus_walk.py     # ④ 逐路由跑官方 H5 抓真实请求 → campus_walk_out.json
python3 campus_test.py        # ⑤ 越权只读扫（F-01/F-02/F-05 检出）
python3 probe_save_route.py   # ⑥ 提交路由存在性判定（三例对照，纯 GET）
python3 trajectory.py         # ⑦ 生成自洽轨迹（只生成本地数据，不发请求）
python3 selfcheck.py          # ⑧ 提交前自查（13 条规则 + 硬否决）
python3 submit_run.py <art>   # ⑨ 提交编排：默认 dry-run；--live 需二道闸
```

> **后续补充**：仓库另含统一入口 `submission/cli.py`，其子命令就是上面这些步骤的**薄包装**
>（不改逻辑、不新增能力），用途是省去逐步调用。此处只作指向，不并入上表。

## 附录 A：真实记录的格式契约（用于服务端校验参照）

```json
{"id":89740,"schoolId":5,"fenceId":16,
 "start":"2026-10-16 09:49:03","end":"2026-10-16 10:04:54",
 "distance":2.54,"duration":951,"pace":"6′14″","step":2558,
 "status":2,"reason":"11,30,40","ddPoints":0,"receive":true,
 "innerNum":191,"outerNum":0,"checkInNum":0,
 "trajectory":"","checkInJson":"","trajectoryUrl":"",
 "reasonFormat":[{"type":1,"reason":"满足打卡点要求；"}, …],
 "dateFormat":"2026年10月16日 09:49-10:04"}
```

| 字段 | 契约（实测） |
|---|---|
| `distance` | **km**（float，下发时四舍五入 2 位；内部计算用未舍入值） |
| `duration` | **秒**（long） |
| `pace` | 字符串 `{分}′{秒:02d}″`（U+2032 `′` / U+2033 `″`，**非** ASCII 引号） |
| `trajectory` | `[[{"longitude":…,"latitude":…}, …]]` —— 外层段数组（实测真实记录**只有 1 段**），点对象**只有经纬度**（无时间/速度/精度） |
| `checkInJson` | 实测为**空串**（即使 `checkInNum=3`） |
| `status` | 1 有效 / 2 无效 |
| `reason` | 逗号分隔判定码；文案由服务端 `reasonFormat` 下发 |

**提交表单 13 字段**（来自原生 `SportApiService` 的 `@FormUrlEncoded` 注解，顺序即注解顺序）：
`schoolId, fenceId, start, end, distance, duration, pace, step, innerNum, outerNum, checkInNum, trajectoryUrl, checkInJson`

## 附录 B：方法学要点（可复用）

1. **让官方客户端自己跑**：H5 注入 token + 网络层读取真实请求，比手拼请求快一个数量级，参数必真。
2. **主机别猜**：本模块在 `school-api.dingxinwen.cn`（不在 `api.topnews.cn`，也不在 `project-api.dingxinwen.cn/noweb/DDCampusRun`）。
3. **方法别猜**：`403 不支持的请求类型` = **方法错**，不是无权限 —— 据此发现读接口可能是 POST。
4. **参数别猜**：`topList` 少一个 `type` 就 500；逐路由抓一遍即全。
5. **文案别信**：`loginStatus:1` 不是成功而是"需拖滑块"；`手机号格式有误` 不是号码问题。
6. **判据要选对**：判断越权不能用"响应里有没有作者字段"，要用"响应记录的 `schoolId` 与我档案是否一致"——
   我们最初正因判据选错，把已确认的 P0（F-01）降级成了"疑似"。
7. **服务端自己会交代**：`reasonFormat` 这类"翻译字段"往往直接给出内部码表，优先找它，别硬啃客户端。
