## 2. 抄的时候"对不上"的地方（必须改，否则等于抄错）

参考项目校验的是**含逐点时间戳/精度/传感器**的完整 trace；我们的目标
`POST /api/runRecord/save` 的 `trajectory` **只有经纬度**。实测真实记录：

```json
{"trajectory":"[[{\"longitude\":…,\"latitude\":…},…]]",   // 外层 1 段；点只有经纬度
 "trajectoryUrl":"", "checkInJson":""}                   // 两个字段都是空串
```

| 参考项目的规则 | 在我们目标上 | 处理 |
|---|---|---|
| `accuracy_stability`（精度方差） | 载荷**无精度字段** ⇒ 服务端拿不到 | **不适用**，标 `applicable=false` |
| `sensor_consistency`（速度-步频相关） | **无传感器字段** | **不适用** |
| `speed_physiological`（逐点瞬时速度） | 无逐点时间 ⇒ 服务端只能按**统一采样间隔**近似 | 改为 `no_teleport`（上限 12 m/s）+ `speed_variance` |
| `noise_spectrum`（位移自相关） | 位移序列仍可从经纬度算出 ⇒ **适用** | 保留（阈值 0.3） |
| `step_distance` | `step` 是客户端自报 ⇒ 自洽性可查 | 保留（步幅基点 0.7、比值 0.4~2.5） |
| 轨迹"层圈"概念（Neko 每 1000m 切圈） | 真实记录**外层只有 1 段** | **不切圈**（candidate 常数 `split_segments=1`） |
| 坐标系转换 WGS84→GCJ02 | 两套参考工程**都没有**；我们的点直接取自服务端下发的围栏多边形 ⇒ 同坐标系 | **不需要**（且这是自洽的关键） |
| 打卡点 `checkInJson` 结构 | 真实记录是**空串**（<他人记录> 即使 `checkInNum=3` 也是 `''`） | 生成空串，自查接受空串 |

**我们新增 4 条本目标专属规则**（服务端真能算、且我们已从真实记录反推公式）：
`pace_formula`、`geometry_selfconsistent`（坐标串长度 vs 上报里程）、`no_teleport`、`not_static`。

## 3. 我们自己做出来、参考项目都没有的

| 能力 | 说明 |
|---|---|
| **里程标定** | GPS 噪声虚增 15~25%，所以 `--km` 指**上报里程**，迭代反解理想行走里程；且**只从下方收敛**，避免四舍五入后跌破达标线 |
| **配速外环标定** | 停走段/起跑坡/末段减速会抬高时长 ⇒ 只标里程会得到 8′12″。必须再按 (实测配速/目标配速) 缩放速度（实测 24 个种子：23/24 落在 ±3% 内，最差 −4.8%；超差时 `check_rules` 会打印告警） |
| **围栏内缩自适应 + 内切圆兜底** | "朝质心收缩"对**凹多边形**不是真内缩（校区9 在 150m 内缩下仍有 9~29 个外点）；圆一定在内 ⇒ 任意形状都有解 |
| **硬否决闸门** | 见 §5 |
| **提交台账/幂等** | 见 §1 #14 |

> **2026-10-18 修正（自曝）**：配速外环迭代原先**返回最后一次**的结果 —— 但"配速 → 缩放系数"
> 是个**带噪声的映射**（缩放速度会改变时长 ⇒ 改变采样点数 ⇒ 换掉噪声实现），定点迭代会震荡，
> 取最后一跳等于取到震荡的波峰（实测个别种子偏到 4′58″ / 7′10″）。已改为**取迭代中偏差最小的
> 一版**并给更新式加 0.7 次幂阻尼；另把胜出候选的 `speedScale` 改为取**该候选自己**的标定结果
> （原先拿的是最后一轮 margin 的返回值，与 `best` 不是同一次标定）。
> **教训**：迭代法的返回值必须锚在"最好的一次"，不是"最后一次"。

## 5. 参考项目的两个错（我们没抄，并已修正）

### 5.1 风险分被平均稀释 ⇒ 做不了"闸门"（budaolepao）
`RiskScorer.score()` 是简单加权平均：单条 `route_novelty` 打 0.8，在 13 条规则里被平均成 **0.06**，
判永远到不了 `medium`(0.6)。我们实测复现了这个现象（同 seed 复用路线 → 规则命中但判定仍是 `normal`）。
**修正**：保留加权平均作为**辅助风险分**，另加**硬否决** —— 任一标记 `hard` 的规则失败即 `REJECT`，不参与稀释。
> 这是"作为检测系统 vs 作为提交闸门"的用途差异，不是他们写错了。

### 5.2 文档与实现脱节（Neko）
README 让人以为 `10121 设备风险` / `10603 点位限流` 有分类处理逻辑；
实际全仓库 grep：两个码**只出现在注释、README 和单测里**，没有任何处理分支。
10603 是靠**预防式 300s 单槽缓存**规避，10121 是靠身份稳定 + 主动拒绝前置健康检查。
**教训**：社区项目的 README 不能当实现证据 —— 我们的 `越权测试报告` / `模块逆向.md` 都已按
「observation / inference / unknown」三分法标注。

## 6. ★ 白噪声检测**不能靠调噪声参数过**，必须复刻客户端的卡尔曼平滑

自查规则 `noise_autocorr`（来自 budaolepao `noise_spectrum`）一开始**时好时坏**（实测 0.05 ~ 0.89）。
先加"闭环重试加大噪声自相关 ρ"，**无效**。于是停止猜测，把三个量分开量出来（实测数据）：

| 被测序列 | lag-1 自相关 | 结论 |
|---|---|---|
| 速度序列（改 OU 平滑后） | **+0.876 / +0.933** | 很平滑 ✓ |
| **纯运动位移**（无噪声） | **+0.838 / +0.929** | 很平滑 ✓ |
| 叠加 AR(1) 噪声 ρ=0.86 | **+0.047** | ✗ 崩塌 |
| 叠加 AR(1) 噪声 ρ=0.95 | **+0.071** | ✗ 几乎没救回来 |

**根因**：位移 = 速度×dt + **噪声增量**，而"相邻点位移"本质是 AR(1) 噪声的**一阶差分** ——
**对自相关过程做差分，结果就是白的**。所以 ρ 从 0.86 提到 0.95 只把 0.047 抬到 0.071。

**正解**：真实客户端**上传前本来就做卡尔曼滤波**（本项目 10-10 报告已从 dex 读到
`utils/sport_map/PathSmoothTool → kalmanFilter(...)`；lepao3 的模板也自带平滑 GPS 噪声）。
补上这一步后：

| 校区 | 位移 lag-1 自相关（5 个随机种子） | 最低 | 里程 |
|---|---|---|---|
| 7（围栏16） | 0.70 / 0.76 / 0.65 / 0.66 / 0.72 | **0.65** ✅ | 2.51~2.55 |
| 8（围栏17） | 0.91 / 0.69 / 0.71 / 0.91 / 0.90 | **0.69** ✅ | 2.51~2.55 |
| 9（围栏18） | 0.66 / 0.78 / 0.60 / 0.65 / 0.78 | **0.60** ✅ | 2.51~2.55 |

实现：`trajectory.py::kalman_smooth`（逐轴一维卡尔曼，q=1e-9，r=2.5e-9/6e-9 择优）；
平滑点若越界则退回未平滑点（凹围栏保护）。

> **方法论**：这条和社区"轨迹自然性"的经验同源 —— **不要对抗检测器，去复刻客户端本来就做的处理**。
> 参考项目里 lepao3 靠"真人模板 + 平滑 GPS 噪声"绕开，Neko 靠"抖动只加坐标、不动弧长"解耦；
> 我们走的是第三条：**照抄客户端自己的滤波器**。

## 7. 提交链路的**结构**判断（本节的结论，不含操作步骤）

分析到后期，真正需要回答的不是"每一步怎么敲"，而是：

```text
提交一条记录这件事，被拆成了两条通道 ——
  通道一：业务网关（H5 那套签名）  → 提交本身走这里，最省事
  通道二：原生主 API（AES-192）    → 对象存储的临时凭证走这里
```

**这个结构判断本身就是产出**，因为它决定了三件事：

1. **提交不必走最难的那条路** —— 业务网关已经开放了提交，省掉整个原生签名体系；
2. **但"轨迹从哪来"被留在了另一条通道** —— 官方设计是"取临时凭证 → 上传到官方桶 → 拿对象地址 → 提交"，
   凭据与桶策略双重约束；
3. **一旦通道二被绕过而通道一不校验来源，两条约束就同时失效** ——
   这正是缺陷 F-07 的本质（详见 `docs/04`）。

> ⚠️ 具体的接口清单、字段契约与验证方法在 `docs/08` 与 `docs/09`；
> 本节刻意不写"分几步、每步打哪个地址"——**结论公开，操作步骤不公开**，
> 理由见 `docs/04 §7`。
