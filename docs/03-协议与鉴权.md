# 03 · 协议与鉴权

> 这一篇回答：**它到底在跟谁说话、说什么、凭什么信？**
>
> 说明：主机名按公开披露口径给出真实值（缺陷已修复并经相关方确认）。
> 但本篇的重点不是"目标清单"，而是**判据** —— 换了任何目标，那部分都成立。

---

## 1. 定址：域名不是后端

### 1.1 三层，不是一个

```text
① 域名(DNS) → ② 接入层(网关/CDN：路由分发、鉴权拦截、套信封、通用拒绝、限流) → ③ 后端服务
```

**你在 ① 看到的"一个域名"，在 ③ 那里可能是完全不同的几套系统。**
而请求**先被 ② 回应** —— 这是所有误判的来源。

### 1.2 本案例的四个标本

| 标本 | 现象 | 教训 |
|---|---|---|
| 同一路径，两个主机 | 同一路径在 A 域回「请登录」、在 B 域回真实业务数据 | **路径相同不能证明主机相同** |
| 同一路径，两个域 | 某登录接口只在 `common` 域存在，但错的那个域**也回「请登录!」** | **通用拒绝长得和正常应答一样** |
| 域名里带业务名 | 某网关域名里嵌着业务名，却是**另一套签名体系**，实测拒签 | 命名反映**部署单位**，不反映**调用关系** |
| 业务被拆到多域 | 业务 / 积分 / 登录风控 / 静态资源，**四个域** | "一个模块一个域"是错的 |

### 1.3 判据

| 判据 | 强度 | 为什么 |
|---|---|---|
| "能连上 / 不是 404" | ❌ | 网关的**通用拒绝**也不是 404 |
| "回了 JSON / 有 `code`" | ❌ | 信封是中间件加的，与路由存不存在无关 |
| "域名或路径里带业务名" | ❌ | 命名 ≠ 部署 |
| **业务载体自己的请求里出现该主机** | ✅ **强** | 行为证据：它必须是对的，否则它自己活不了 |
| **响应里出现只有业务才知道的东西** | ✅ **强** | 例：我的真实学期名与学期 id |

> **照妖镜用法**：打到新主机后，先把"只有对的后端才知道的东西"记下来。
> 之后打任何路径，用它验证：**说不出这些事的，就不是业务后端。**

**最快的定址方式**：让**业务载体自己跑**（官方 H5 / 官方客户端），从网络层抄它的主机。

## 2. 统一信封：为什么 `code` 不能当判据

```json
{"code":0, "msg":"OK", "time":…, "data":{…}}
```

信封由**中间件**产生，位置比"路由存不存在"更早 —— 所以它**对路由一无所知**。
而它把三个层级的语义压进了同一个字段：

| 响应 | 谁产生的 | 层级 |
|---|---|---|
| `{"code":0,…}` | 业务逻辑 | 业务层 |
| `{"code":1,"msg":"无权限访问教师端"}` | 业务鉴权 | 业务层（拒绝） |
| `{"code":403,"msg":"不支持的请求类型"}` | 框架/路由分发 | **框架层（方法不对）** |
| `{"code":500,"msg":"系统异常"}` | 异常兜底 | 异常层（**缺参数也会 500**） |
| `HTTP 404` + 网关 JSON | **网关**（连信封都没有） | 路由前 |
| `请登录`（纯文本） | 通用登录拦截 | 连信封都没有 |

**最后两行是重点**：最常见的两种失败**根本没进信封**，
而且它们**最容易被读成"差一步就成功"**。

### 分层判据（照这个顺序读响应）

| 层 | 看什么 | 强度 | 能回答 |
|---|---|---|---|
| 1 | HTTP 状态 | ⚠️ | 是否到达应用 |
| 2 | **有没有信封** | ✅ | **没有 ⇒ 你还没到业务层** |
| 3 | `code` | ⚠️ | 到业务层后的粗分类 |
| 4 | **`data` 里有没有只有业务才知道的东西** | ✅ **强** | ★ "我打对了吗" |

## 3. 确认一个端点存在：三例对照

**单个响应说明不了任何事 —— 要给未知量找"已知锚点"。**

| 用例 | 路径 | 响应 | 判读 |
|---|---|---|---|
| A 基准：不存在 | 明显占位路径 | `HTTP 404` + 网关 JSON（**无信封**） | 不存在长这样 |
| C 基准：存在但方法错 | 已知 POST-only 的读接口 | `{"code":403,"msg":"不支持的请求类型"}` | 存在但方法错长这样 |
| **B 目标** | 待确认的写接口 | 与 C **同形** | ⇒ **存在** |

### 两个要点

**① 用错误方法打写接口 = 零副作用探测。**
路由匹配后立刻因方法不对被拒，**业务逻辑一行都不执行**。

**② 偶发异常必须重测才能定性。**
首次探测出现过一次超时（同时刻另外两例都秒回），重试 2/2 稳定复现 ⇒ 判为瞬时抖动。
**不重测就下结论 = 把噪声当信号。**

### 反查表（直接照用）

| 响应 | 含义 |
|---|---|
| `HTTP 404` + 网关 JSON（无信封） | 路径不存在 |
| `请登录` / `用户未登录` | 到达鉴权层 —— **它不知道路径存不存在** |
| `{"code":403,"msg":"不支持的请求类型"}` | **路径存在**，方法不对 |
| `{"code":1,"msg":"无权限…"}` | 路径存在、方法对、**鉴权拒绝** |
| `{"code":500}` | 到了业务层但炸了 —— 常见原因是**缺必填参数** |
| `{"code":0,…}` + 业务数据 | 全通 |

## 4. 鉴权：同一家公司并存两套

| 维度 | 原生（App 发的） | H5（网页发的） |
|---|---|---|
| 明文拼法 | 排序后 `k=v` **无分隔**拼接 | 同（一致） |
| 中间有无加密 | **有**：AES-192-CBC-PKCS7 → base64 | **没有** |
| secret 来源 | so / native getter | **明文写在入口 JS 里** |
| **token 放哪** | 请求头 | **query 里，且参与签名** |
| token 形态 | 原样 | **必须带前缀** |
| 拿证难度 | 高（要 native） | **低（读 JS）** |

### 判据：该用哪一套

> **看这条请求是谁发的。** 不是"哪套能过就用哪套"。

这不是习惯问题，是**构建方式决定的**：原生侧在 OkHttp 拦截器里自动加签；
H5 拿不到编译进 so 的密钥。**两套不是新旧版本，是两套并行的身份。**

### 三个真实的坑

| 坑 | 现象 | 说明 |
|---|---|---|
| token 位置错 | `{"msg":"sign:签名校验失败"}` | 它说的是**签名失败**，不是"token 无效" ⇒ **位置本身就是签名约定的一部分** |
| 前缀去掉 | `{"code":-1,"msg":"用户未登录"}` | **纯约定、无算法含义** ⇒ 只能从**真实请求**里看出来 |
| 拦截器的"逃生门" | 有些请求没签名 | 真字节码里有：`if (query 里已存在某参数) return request;` ⇒ 自己带该参数就跳过签名 |

### 怎么知道签名复刻对了

**唯一够硬的判据：与官方自签样本逐字符比对。**

| 判据 | 够硬？ |
|---|---|
| "我算出的 sign 看起来像个 md5" | ❌ 任何错算法都像 |
| "服务端返回 `code:0`" | ❌ 通用拒绝/缓存/免签路由都可能 |
| ✅ "与 app 自签样本**逐字符**相同（2/2）" | ✅ |

### 反直觉但决定成败的细节

| 细节 | 猜错会怎样 |
|---|---|
| AES 是 **192 位**（key 24 字节） | 用 128 位 ⇒ 签名全错，**不报错** |
| 参数对之间**无分隔符** | 加 `&` ⇒ 全错 |
| 参数值取 **URL 解码后**的值 | 用编码后的 ⇒ 全错 |
| 排序用 **String.compareTo** 自然序 | locale 排序 ⇒ **一批接口通、一批死**（最难查） |
| 输出是**标准 Base64** | 去填充 ⇒ 全错 |

> 第 4 条最狠：它只在参数名大小写混排时暴露，
> 第一反应必然是"那几个接口有额外校验"，然后在错的方向上耗一天。

## 5. 把官方客户端当 oracle

**它本来就能工作** —— 所以它必须能签对、拼对、算对。

| 类型 | 怎么问 | 本案例 |
|---|---|---|
| ① 给输入要输出 | 让它用真实逻辑算一次 | 反射调用拦截器 → 拿到**带正确签名的完整 URL** |
| ② 用它做对照 | **只改一个量**，看输出变不变 | 拿三个**完全不同的 path** 问，签名**完全相同** ⇒ 证明签名不含 path |
| ③ 让它自证 | 让它在自己进程里跑一遍你的公式 | 进程内 `MATCH=true` + 纯 Python 2/2 |

**第 ② 类威力最大**：证明签名不含 path ⇒ 工作量从"逐接口解"变成"一次解"。

### 三条纪律

| 纪律 | 说明 |
|---|---|
| **先答题，再对答案** | 在见过的样本上一致，什么都不能证明 |
| **能复现 ≠ 能解释** | 要改它、评估它，常常需要解释 |
| **oracle 不是白来的** | 它要求**能驱动**；驱动不了就去找"能被驱动的同构物"（网页/小程序/旧版本） |

## 6. 响应即规格

| 来源 | 给什么 | 权威度 |
|---|---|---|
| 注释 / 文档 | 作者当时认为的样子 | ❌ 会过期、会撒谎 |
| 编译期元数据（注解） | **字段名与结构** | ⚠️ 只给名字，**不给值的形状** |
| **运行时响应样本** | 结构 + 格式 + **字段之间的关系** | ✅ **最强** |

### 三层，第三层是分水岭

| 层 | 内容 | 本案例 |
|---|---|---|
| ① 结构 | 字段/嵌套/可选性 | 轨迹是"外层段数组 + 内层点对象"，点里**只有经纬度** |
| ② 格式 | 单位/精度/字符 | 距离单位 km；配速串用的是 **U+2032/U+2033**，不是 ASCII 引号 |
| ③ **规则** | 字段之间怎么互相制约 | `pace = duration ÷ distance`，而这里用的是**未四舍五入**的距离 |

**第 ③ 层只存在于实现里** —— 只能从样本反推。

### 一次"舍入"暴露算法（本篇最漂亮的推理）

```text
① 119s ÷ 0.68km = 175s/km = 2′55″   ← 与记录一致 ✅
② 252s ÷ 0.35km = 720s/km = 12′00″  ← 记录写的是 12′07″ ❌ 差 7 秒
```

**别停在这里下"公式错了"的结论。** 反推：`12′07″ = 727s` ⇒ 距离 ≈ **0.3466**
⇒ 四舍五入到 2 位 = **0.35** ✅ ⇒ **下发的是舍入值，内部用的是未舍入值。**

**容差不能固定，必须与量级相对**：距离越小，同样的舍入在配速上放得越大
（2.5km → 0.2%；0.35km → 1.4%，约 7 倍）。

### 至少要看两条样本

一条样本只能告诉你"这样是合法的"，**分不清"必然"和"偶然"**。
**多条来源不同的样本，一致的部分才是契约。**
最硬的判据：**用契约反推，能对上原始值**（说明抓到的是真算法，不是凑出来的近似式）。
