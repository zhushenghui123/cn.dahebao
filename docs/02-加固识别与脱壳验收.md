# 02 · 加固识别与脱壳验收

> 这一篇回答两个问题：**① 这是哪一层在保护代码？② 我脱壳到底成了没有？**
> 这是全项目最容易自欺的两道闸门。

---

## 1. 加固识别：交证据表，不要交名字

成熟规则库（APKiD 一路下来的格式）都用同一个结构，四类判据：

| 判据 | 看什么 | 为什么可靠 |
|---|---|---|
| `sopath` | 某文件的**完整路径** | 壳引擎要能被加载，路径就得固定 |
| `soname` | `.so` 的**文件名** | 引擎名是硬的 |
| `other` | 载荷/配置文件的**存在** | 加密载荷必须随包走 |
| `soregex` | 文件名**形态**（`libxxx_*.so`） | 覆盖同族多变体 |

**四类合起来指同一件事**：

```text
一个必须被加载的引擎（在哪 + 叫什么）+ 一份必须随包的载荷（是什么）
= 这个壳逃不掉的指纹
```

> 它们全是**存在性**判据 ⇒ 识别可以在解包阶段完成，甚至不用跑。
> 代价：**只能告诉你"这里有壳"，告诉不了你"这壳在干什么"。**

---

## 2. 多命中是常态，不是规则库不准

| 原因 | 说明 |
|---|---|
| 厂商**代际标记共存** | 新一代保护往往沿用老引擎/载荷名，同时新增自己的 |
| 一个 App 可能**同时用多家** | 壳 + 风控 SDK + 自研保护 |
| 规则是"**或**"关系 | 命中任一判据就报一家 |

### 本案例实测：一个包，三组命中

```text
爱加密（基础）    ：assets/ijm_lib/<abi>/libexec.so、libexecmain.so、ijiami.dat
爱加密5代壳       ：assets/libijmDataEncryption.so、assets/IJMDal.Data
爱加密企业版      ：assets/ijiami.ajm
```

**三组都真的在包里。** 但它们的**作用对象不一样**：

| 命中 | 作用对象 |
|---|---|
| `ijiami.dat`（22 MB，头 0x28 = `u32=4` + `u32=解密后长度` + 32 字符 hex） | ★ **加密的 dex 容器** |
| `ijm_lib/<abi>/libexec.so`（按 ABI 分发） | 加载并解密上面那个容器 |
| `ijiami.ajm`（9.8 MB，magic `indl01`） | 企业版额外保护层 |
| `libijmDataEncryption.so` + `IJMDal.Data` | ⚠️ **本地数据加密，不保护 dex** |

### ★ 判"哪一层管 dex"（本篇最重要一条）

判据不是"哪一代最新"，而是：

```text
① 这一层的载荷里，有没有【dex 容器特征】？（容器头自洽 / magic / 声明长度匹配）
② 有没有谁在加载它？（加载点可定位 ⇒ 它真的在跑）
③ 作用对象是数据/日志/配置的那一层，直接排除
```

**认错对象的代价**：对"数据加密层"做 dex dump ⇒ **整条流程白忙**。

## 3. 脱壳验收：三种假状态

**dump 最容易骗人的地方：手段成功了，目的失败了。**

| # | 假状态 | 看起来像什么 | 真实含义 |
|---|---|---|---|
| 1 | **桩 dex** | 文件有效、能解析、能被 jadx 打开 | 里面**只有壳的引导类** |
| 2 | **占位 dex** | `.cache/classes*.dex` 名字很像 | **只有 magic、没有内容** ⇒ "内存加载正在发生"，不是成功提取 |
| 3 | **同一份反复 dump** | 一堆不同时间点的文件 | 同一个 **sha256** 出现多次 ⇒ **时机根本没变** |

**第 3 条最容易被忽略**：目录里躺着 7 个文件，看着很勤奋，其实是**同一份**。
⇒ **看文件数量没有意义，看内容的多样性才有意义。**

本案例的桩 dex 真实长相：

```text
classes.dex      13,868 字节
字符串数         193 个
含有             s.h.e.l.l.{A,C,N,S}（壳自己的引导类）、libexec
不含有           业务包名、业务入口类、任何签名相关方法
```

## 4. 三条硬验收判据（缺一不可）

| # | 判据 | 排除什么 |
|---|---|---|
| 1 | dumped dex **含非桩业务逻辑** | 桩 dex |
| 2 | 抽取壳额外看：目标方法 `codeItem` 非空 / **`invoke` 数量回升** | "文件完整但方法体被抽走" |
| 3 | 能**绑回目标包名 + 版本** | "dump 到了别的东西" |

**第 2 条的可数实例**：

```text
同一个类、同一个文件：
  注入强制类加载之前：  invoke 数量 = 1
  注入之后：            invoke 数量 = 283     ← 可数、可复现、可对比
```

### 一条更本质的判据：能不能回答我的问题

```text
这一堆 dex 里，有没有我这次任务要的那些类？
（目标包名 / 业务入口 / 请求与签名代码 / native 桥引用）
```

**即使一份 dex 完整有效、体积可观，只要里面没有你要的类，对这次任务就是"没拿到"。**

## 5. 抽取壳：按什么触发，以及怎么主动触发

### 5.1 先验伪：排除"是工具读不出来"

**不能再用同一个工具** —— 换一个独立实现的解析器（例：AOSP `dexdump`）：

```bash
dexdump -d classes4.dex | grep -A3 "name.*<init>"
#   insns size : 7 16-bit code units      ← 指令真实存在
```

两个结论同时成立才算清楚：

| 结论 | 证据 |
|---|---|
| 字节码**在** dex 里（不是文件损坏） | 独立解析器能读出指令流 |
| 但它是 **`nop` 骨架**（不是工具问题） | 连独立解析器看到的也是占位代码 |

### 5.2 对照实验：定位触发点（本项目最有价值的一步）

| 类 | 为什么选它 | `nop` | `invoke` |
|---|---|---|---|
| 真实 Application | **必然被加载** | **0** | **45** |
| 同 dex、无引用的类 | **必然没被加载** | 558 | 0 |
| 业务类（未加载） | —— | 1742 | 1 |

⇒ **触发点 = 类加载**（不是按 dex：同 dex 内两种状态并存；
不是按方法首次执行：Application 的 45 个 `invoke` 不可能都被执行过）。

**附带观察**：已还原的类**连 `.line` 行号都在** ⇒ 壳是把**完整原始字节码**写回去的。

### 5.3 注入点选择

| 候选 | 评估 |
|---|---|
| 壳的 `<clinit>` | ❌ 太早 —— 真实 `ClassLoader` 还不存在 |
| `instantiateClassLoader` | ⚠️ 混淆严重，patch 风险高 |
| **`instantiateApplication`** | ✅ 参数就是真实 `ClassLoader`，且**早于所有业务代码** |

### 5.4 一条必须有的工程细节

```text
对目标类逐个 Class.forName，【每个类单独 try/catch】
```

**为什么决定成败**：批量里只要一个抛异常且共用一个 try，**后面全部不执行**；
而"哪些类加载失败"**本身也是信息**。

## 6. 被加固改造过的 ELF（顺带必有）

| 结构 | 谁需要它 | 能不能改坏 |
|---|---|---|
| **程序头表**（`PT_LOAD`/`PT_DYNAMIC`） | ★ **动态链接器** | ❌ 不能 —— 改坏了它自己起不来 |
| **节表**（`.text`/`.symtab`/`.dynsym`） | 链接器、调试器、**分析工具** | ✅ 能 —— 运行时用不到 |

⇒ 常见手法：**破坏节表**。后果：`readelf --dyn-syms` 报错、
`pyelftools.iter_sections()` 报错**或给假数据**（后者更危险）。

**正解：只读 loader 必须的那部分。**

```text
ELF 头 → 程序头 → PT_DYNAMIC → DT_SYMTAB / DT_STRTAB / DT_STRSZ / DT_HASH
DT_HASH 的 nchain 直接等于符号表项数（不用去数节表）
```

**但要分清两件事**：符号表修复解决「**工具读不了**」，
不解决「**符号本来就不存在**」（运行时 `RegisterNatives` 绑定的方法，so 里没有 `Java_...`）。

> **用"没搜到"下结论之前，先拿一个"已知一定存在"的样本验证你的搜索方法。**
> 本项目真的翻过车：扫字符串时**连已知一定被引用的都 0 命中** ⇒
> "没找到"反映的是**方法坏了**。

## 7. 验收清单

```text
【加固识别】
[ ] 命中家族全部列出（含路径/文件名）
[ ] 指定了哪一层管 dex，并给出判据（容器头 / magic / 被谁加载）
[ ] 交叉验证过（两个独立来源）

【脱壳】
[ ] 文件数 > 1 时，先按 sha256 去重（重复 = 时机没变）
[ ] 每个 dex：magic 有效？体积/字符串数量级合理？
[ ] 里面有目标包名吗？有业务入口类吗？
[ ] 抽取壳：目标方法 codeItem 非空吗？invoke 回升了吗？
[ ] 有没有只带 magic 的占位 dex？（那是"加载中"，不是成果）
[ ] 最终：现在的产物能支撑任务的下一步吗？
```
