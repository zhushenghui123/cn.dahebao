# 03 · 协议与服务端判定

> 本文件解决：**它到底在跟谁说话、说什么、凭什么信？**
> 适用：找真后端、确认端点存在、复刻签名、还服务端判定规则、从响应反推格式契约。

---

## 1. 定址：域名不是后端

### 1.1 三层，不是一个

```text
① 域名(DNS) → ② 接入层(网关/CDN：路由分发、鉴权拦截、套信封、通用拒绝、限流) → ③ 后端服务
```

**你在 ① 看到的"一个域名"，在 ③ 那里可能是完全不同的几套系统。**
而请求**先被 ② 回应**——这是所有误判的来源。

### 1.2 四个真实标本

| 标本 | 现象 | 教训 |
|---|---|---|
| 同一路径，两个主机 | `/api/semester/currSemester` 在 A 域回「请登录」、在 B 域回真实学期数据 | **路径相同不能证明主机相同** |
| 同一路径，两个域 | `user/risk/sms/sendCode` 只在 `common` 域存在，但错的那个域**也回「请登录!」** | **通用拒绝长得和正常应答一样** |
| 域名里带业务名 | `…/noweb/DDCampusRun` 名字里有业务，却是**另一套签名体系**，实测拒签 | 命名反映**部署单位**，不反映**调用关系** |
| 业务被拆到多域 | 业务 / 积分 / 登录风控 / 静态资源，**四个域** | "一个模块一个域"是错的 |

### 1.3 判据

| 判据 | 强度 | 为什么 |
|---|---|---|
| "能连上 / 不是 404" | ❌ | 网关的**通用拒绝**也不是 404 |
| "回了 JSON / 有 `code`" | ❌ | 信封是中间件加的，与路由存不存在无关 |
| "域名或路径里带业务名" | ❌ | 命名 ≠ 部署 |
| **业务载体自己的请求里出现该主机** | ✅ **强** | **行为证据**，它必须是对的，否则它自己活不了 |
| **响应里出现只有业务才知道的东西** | ✅ **强** | 例：我的真实学期名与学期 id |

> **照妖镜用法**：打到新主机后，先把"只有对的后端才知道的东西"记下来（学期名/学号/院系）。
> 之后再打任何路径，用它验证：**说不出这些事的，就不是业务后端。**

**最快的定址方式**：让**业务载体自己跑**（官方 H5 / 官方客户端），从网络层抄它的主机。
（载体是页面时见 §7 SPA 的坑。）

## 2. 统一信封：为什么 `code` 不能当判据

```json
{"code":0, "msg":"OK", "time":…, "data":{…}}
```

信封由**中间件**产生，位置比"路由存不存在"更早 —— 所以它**对路由一无所知**。
而它把三个层级的语义压进了同一个字段：

| 响应 | 谁产生的 | 层级 |
|---|---|---|
| `{"code":0,…}` | 业务逻辑 | 业务层 |
| `{"code":1,"msg":"无权限访问教师端"}` | 业务鉴权 | 业务层（拒绝） |
| `{"code":403,"msg":"不支持的请求类型"}` | 框架/路由分发 | **框架层（方法不对）** |
| `{"code":500,"msg":"系统异常"}` | 异常兜底 | 异常层（**缺参数也会 500**） |
| `HTTP 404` + 网关 JSON | **网关**（连信封都没有） | 路由前 |
| `请登录`（纯文本） | 通用登录拦截 | 连信封都没有 |

**最后两行是重点**：最常见的两种失败**根本没进信封**，
而且它们**最容易被读成"差一步就成功"**。

### 分层判据（照这个顺序读响应）

| 层 | 看什么 | 强度 | 能回答 |
|---|---|---|---|
| 1 | HTTP 状态 | ⚠️ | 是否到达应用 |
| 2 | **有没有信封** | ✅ | **没有 ⇒ 你还没到业务层** |
| 3 | `code` | ⚠️ | 到业务层后的粗分类 |
| 4 | **`data` 里有没有只有业务才知道的东西** | ✅ **强** | ★ "我打对了吗" |

## 3. 确认一个端点存在：三例对照

**单个响应说明不了任何事 —— 要给未知量找"已知锚点"。**

| 用例 | 路径 | 响应 | 判读 |
|---|---|---|---|
| A 基准：不存在 | `/api/__no_such_path__` | `HTTP 404` + 网关 JSON（**无信封**） | 不存在长这样 |
| C 基准：存在但方法错 | 已知 POST-only 的读接口 | `{"code":403,"msg":"不支持的请求类型"}` | 存在但方法错长这样 |
| **B 目标** | 待确认的写接口 | 与 C **同形** | ⇒ **存在** |

### 两个要点

**① 用错误方法打写接口 = 零副作用探测。**
路由匹配后立刻因方法不对被拒，**业务逻辑一行都不执行**。
这是"在不触发副作用的前提下确认写接口存不存在"的标准手法。

**② 偶发异常必须重测才能定性。**
首次探测 B 时出现一次超时（同一时刻 A 与 C 都秒回），重试 2/2 稳定复现 ⇒ 判为瞬时抖动。
**不重测就下结论 = 把噪声当信号。**

### 反查表（直接照用）

| 响应 | 含义 |
|---|---|
| `HTTP 404` + 网关 JSON（无信封） | 路径不存在 |
| `请登录` / `用户未登录` | 到达鉴权层 —— **它不知道路径存不存在** |
| `{"code":403,"msg":"不支持的请求类型"}` | **路径存在**，方法不对 |
| `{"code":1,"msg":"无权限访问教师端"}` | 路径存在、方法对、**鉴权拒绝** |
| `{"code":500}` | 到了业务层但炸了 —— 常见原因是**缺必填参数** |
| `{"code":0,…}` + 业务数据 | 全通 |

## 4. 鉴权：先分清有几套

**同一家公司常常并存两套签名/凭据体系。** 真实对比：

| 维度 | 原生（App 发的） | H5（网页发的） |
|---|---|---|
| 明文拼法 | 排序后 `k=v` **无分隔**拼接 | 同（一致） |
| 中间有无加密 | **有**：AES-192-CBC-PKCS7 → base64 | **没有** |
| secret 来源 | so / native getter | **明文写在入口 JS 里** |
| **token 放哪** | 请求头（`user_token`） | **query 里，且参与签名** |
| token 形态 | 原样 | **必须带前缀**（如 `u_token:`） |
| 拿证难度 | 高（要 native） | **低（读 JS）** |

### 判据：该用哪一套

> **看这条请求是谁发的。** 不是"哪套能过就用哪套"。

这不是习惯问题，是**构建方式决定的**：原生侧在 OkHttp 拦截器里自动加签；
H5 拿不到编译进 so 的密钥。**两套不是新旧版本，是两套并行的身份。**

### 三个真实的坑

| 坑 | 现象 | 说明 |
|---|---|---|
| token 位置错 | `{"msg":"sign:签名校验失败"}` | 它没说"token 无效"，说的是**签名失败** ⇒ **位置本身就是签名约定的一部分** |
| 前缀去掉 | `{"code":-1,"msg":"用户未登录"}` | **纯约定、无算法含义** ⇒ 只能从**真实请求**里看出来 |
| 拦截器的"逃生门" | 有些请求没签名 | 真字节码里有：`if (query 里已存在 app_id) return request;` ⇒ **自己带 app_id 就跳过签名** |

### 怎么知道签名复刻对了

**唯一够硬的判据：与官方自签样本逐字符比对。**

| 判据 | 够硬？ |
|---|---|
| "我算出的 sign 看起来像个 md5" | ❌ 任何错算法都像 |
| "服务端返回 `code:0`" | ❌ 通用拒绝/缓存/免签路由都可能 |
| ✅ "与 app 自签样本**逐字符**相同（2/2）" | ✅ |

### 反直觉但决定成败的细节

| 细节 | 猜错会怎样 |
|---|---|
| AES 是 **192 位**（key 24 字节） | 用 128 位 ⇒ 签名全错，**不报错** |
| 参数对之间**无分隔符** | 加 `&` ⇒ 全错 |
| 参数值取 **URL 解码后**的值 | 用 `%20` ⇒ 全错 |
| 排序用 **String.compareTo** 自然序 | locale 排序 ⇒ **一批接口通、一批死**（最难查） |
| 输出是**标准 Base64** | 去填充 ⇒ 全错 |

> 第 4 条最狠：它只在参数名大小写混排时暴露，第一反应必然是"那几个接口有额外校验"。

## 5. 把官方客户端当 oracle

**它本来就能工作** —— 所以它必须能签对、拼对、算对。三类可问的问题：

| 类型 | 怎么问 | 实例 |
|---|---|---|
| ① 给输入要输出 | 让它用真实逻辑算一次 | 反射调拦截器 → 拿到**带正确 sign 的完整 URL** |
| ② 用它做对照 | **只改一个量**，看输出变不变 | 拿三个**完全不同的 path** 问，`sign` **完全相同** ⇒ 证明签名不含 path |
| ③ 让它自证 | 让它在自己进程里跑一遍你的公式 | 进程内 `MATCH=true` + 纯 Python 2/2 |

**第 ② 类威力最大**，它把 oracle 从"查表器"升级成"实验装置"：
**证明签名不含 path ⇒ 工作量从"逐接口解"变成"一次解"。**

### 三条纪律

| 纪律 | 说明 |
|---|---|
| **先答题，再对答案** | 在见过的样本上一致，什么都不能证明 |
| **能复现 ≠ 能解释** | 要改它、评估它，常常需要解释 |
| **oracle 不是白来的** | 它要求**能驱动**；驱动不了就去找"能被驱动的同构物"（网页/小程序/旧版本） |

## 6. 响应即规格：从真实记录反推格式契约

| 来源 | 给什么 | 权威度 |
|---|---|---|
| 注释 / 文档 | 作者当时认为的样子 | ❌ 会过期、会撒谎 |
| 编译期元数据（注解） | **字段名与结构** | ⚠️ 只给名字，**不给值的形状** |
| **运行时响应样本** | 结构 + 格式 + **字段之间的关系** | ✅ **最强** |

### 三层，第三层是分水岭

| 层 | 内容 | 实例 |
|---|---|---|
| ① 结构 | 字段/嵌套/可选性 | `trajectory = [[{lng,lat},…],…]`：外层**段数组**，点里**只有经纬度** |
| ② 格式 | 单位/精度/字符 | `distance` 单位 **km**；`pace` 用 **U+2032 `′` / U+2033 `″`**，不是 ASCII 引号 |
| ③ **规则** | 字段之间怎么互相制约 | `pace = duration ÷ distance`，而这里的 `distance` 是**未四舍五入**的那个 |

**第 ③ 层只存在于实现里** —— 只能从样本反推。

### 一次"舍入"暴露算法（漂亮的实例）

```text
① 119s ÷ 0.68km = 175s/km = 2′55″   ← 与记录一致 ✅
② 252s ÷ 0.35km = 720s/km = 12′00″  ← 记录写的是 12′07″ ❌ 差 7 秒
```

**别停在这里下"公式错了"的结论。** 反推：`12′07″ = 727s` ⇒ 距离 ≈ **0.3466** ⇒ 四舍五入到 2 位 = **0.35** ✅
⇒ **下发的是舍入值，内部用的是未舍入值。**

**容差不能固定，必须与量级相对**：距离越小，同样的舍入在 `pace` 上放得越大
（2.5km → 0.2%；0.35km → 1.4%，约 7 倍）。

### 至少要看两条样本

一条样本只能告诉你"这样是合法的"，**分不清"必然"和"偶然"**。
**多条来源不同的样本，一致的部分才是契约。**
最硬的判据：**用契约反推，能对上原始值**（说明抓到的是真算法，不是凑出来的近似式）。

**自查工具必须先拿真实样本校准** —— 真实记录过不了，是**规则**错了，不是数据错了。

## 7. 让业务载体自己跑（含 SPA 的坑）

**做法**：打开官方页面（或官方客户端）→ 注入登录态 → **逐个路由走一遍** → 网络层记账。

**两个必须知道的用法**：

| 用法 | 写法 | 请求出网？ | 什么时候用 |
|---|---|---|---|
| **记账** | `on("request", cb)` | ✅ 会 | 走**读**路由 |
| **掐断** | `route(...) → abort()` | ❌ 不会 | 碰**有副作用**的请求（如发短信） |

判据只有一条：**这个请求发出去会不会改变服务端状态？**

**拦截点在"出网之前"** ⇒ 可以做到"**没给任何人发短信，却拿到了完整报文**"。

### SPA 的四个坑

| 坑 | 真相 |
|---|---|
| "打开首页就拿到所有接口" | 每个路由只加载**自己的** chunk 与数据（代码分割 + 懒加载） |
| "换 hash 会重载页面" | 不会，文档不重载 |
| "等 `load` 完成请求就发完了" | 数据请求往往在其**之后** |
| "接口没出现 ⇒ 接口不存在" | 可能只是那个路由**没被访问** |

**要点**：从还原后的 JS 拿路由表 → 逐个访问 → **每次等几秒** →
**判据 = 页面渲染出真实业务内容**（不是"我访问了"）。

### 顺带的启示

**网页不依赖那个安卓壳** ⇒ 加固把运行环境焊死时，"驱动官方前端"是一条独立的路。
当"驱动客户端"走不通，**去找能被驱动的同构物**。

## 8. 还服务端判定：两层 + 码表

### 8.1 两层是独立的

| 层 | 内容 | 拿法 |
|---|---|---|
| **规则层** | "合格线画在哪" | 经常有接口**直接下发**（阈值/时段/次数）—— 便宜 |
| **实算层** | "从数据算出结果" | 只能靠**实验** |

**别因为"它有阈值"就假设"它会实算"。**

### 8.2 判"算不算"的方法

```text
① 上报一个值（让它处在合理范围，不要离谱，否则会触发别的检查）
② 提交 → 回读
③ 逐字段比对：与上报一致 ⇒ 不重算；被改写 ⇒ 重算
```

实测结果（同一份响应里"算了"与"没算"**同时存在**）：

| 字段 | 上报 | 落库 | 重算？ |
|---|---|---|---|
| `distance`/`duration`/`pace`/`step` | 2.54 / 951 / `6′14″` / 2558 | **逐字相同** | ❌ **不重算** |
| `status`（判定） | —— | 服务端给出 | ✅ 有判定 |

**另一方向的证据**：客户端上报"我打了 1 个卡"，而轨迹不经过 ⇒ **仍判不达标** ⇒
**打卡点这一项是实算的，不采信客户端上报的结论。**

> ⇒ 同一服务端：**"数值类字段"照单全收，"结论类字段"自己算。**
> 这决定了攻击面在哪：数值可随便报；结论绕不过去，除非**数据本身**被操控。

### 8.3 码表：文案无极性，`type` 有

```json
"reason": "11,30,40",
"reasonFormat": [{"type":1,"reason":"满足打卡点要求；"}, {"type":0,…}, …]
```

| 码 | 文案 | `type` | 结论 |
|---|---|---|---|
| 10 | 满足打卡点要求 | 0 | 达标 |
| **11** | 满足打卡点要求 | **1** | **不**达标 |
| 40 / 41 | 配速在 3~10 min/Km 之间 | 0 / **1** | 达标 / **不**达标 |

**码 = "哪一条规则"；`type` = "这条规则过没过"；`status` = 汇总（全 0 ⇒ 有效）。**

### 8.4 判据

| 判据 | 强度 |
|---|---|
| "文案说满足 ⇒ 我达标了" | ❌ |
| 多条独立样本交叉，`type` 与 `status` 零冲突 | ✅ 强 |
| **能预测**（只看 `reason` 就能算出 `status`） | ✅ 强 |
| 换一条新记录验证预测仍成立 | ✅ 最强 |

## 9. 清单

```text
[ ] 主机是"行为证据"定出来的（不是猜的/不是 grep 到的）
[ ] 用"只有对的后端才知道的东西"验证过主机
[ ] 端点在不在，用三例对照答的
[ ] 分清了几套签名；token 位置与形态是从真实请求看来的
[ ] 签名复刻与官方样本逐字符比对过
[ ] 完整响应通读过一遍（找过下游的翻译字段）
[ ] 判定分清了规则层 / 实算层；"算不算"是实验答的
[ ] 码表是交叉验证 + 能预测的
[ ] 格式契约来自 ≥2 条不同来源的真实样本
```
