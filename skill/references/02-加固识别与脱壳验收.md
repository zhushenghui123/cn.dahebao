# 02 · 加固识别与脱壳验收

> 本文件解决两个问题：**① 这是哪一层在保护代码？（不是"叫什么名字"）**
> **② 我脱壳到底成了没有？**
> 适用：拿到一个被加固的 APK；或者已经跑完一轮 dump，准备说"成了"的时候。

---

## 1. 加固识别：四类判据，交证据表而不是名字

成熟的规则库（APKiD 一路下来的格式）都用同一个结构：

| 判据 | 看什么 | 为什么可靠 |
|---|---|---|
| `sopath` | 某个文件的**完整路径** | 壳的引擎要能被加载，路径就得固定 |
| `soname` | 某个 `.so` 的**文件名** | 引擎名是硬的 |
| `other` | 载荷/配置文件的**存在** | 加密载荷必须随包走 |
| `soregex` | 文件名**形态**（`libjiagu_xxx.so`） | 覆盖同族多变体 |

**四类合起来指同一件事**：

```text
一个必须被加载的引擎（在哪 + 叫什么）+ 一份必须随包的载荷（是什么）
= 这个壳逃不掉的指纹
```

**它们全是"存在性"判据** ⇒ 识别可以在解包阶段完成，甚至不用跑。
代价是：**只能告诉你"这里有壳"，告诉不了你"这壳在干什么"。**

---

## 2. 多命中是常态，不是规则库不准

三个原因叠在一起：

| 原因 | 说明 |
|---|---|
| **厂商代际标记共存** | 新一代保护往往**沿用**老引擎/载荷名，同时新增自己的 |
| **一个 App 可能同时用多家** | 壳 + 风控 SDK + 自研保护，各留指纹 |
| **规则是"或"关系** | 命中任一判据就报一家 ⇒ 天然容易多家同时命中 |

### 真实例子（一个包，三组命中）

```text
爱加密（基础）    ：assets/ijm_lib/<abi>/libexec.so、libexecmain.so、ijiami.dat
爱加密5代壳       ：assets/libijmDataEncryption.so、assets/IJMDal.Data
爱加密企业版      ：assets/ijiami.ajm
```

**三组都真的在包里。** 关键在于它们的**作用对象不一样**：

| 命中 | 作用对象 |
|---|---|
| `ijiami.dat`（22 MB，头 0x28 = `u32=4` + `u32=解密后长度` + 32 字符 hex） | ★ **加密的 dex 容器** |
| `ijm_lib/<abi>/libexec.so`（按 ABI 分发） | 加载并解密上面那个容器 |
| `ijiami.ajm`（9.8 MB，magic `indl01`） | 企业版额外保护层 |
| `libijmDataEncryption.so` + `IJMDal.Data` | ⚠️ **本地数据加密，不是 dex 保护** |

> ⇒ **"5 代壳"这一组命中的是真的，但它保护的不是 dex。**

### ★ 判"哪一层管 dex"（本文件最重要的一条）

判据不是"哪一代最新"，而是：

```text
① 这一层的载荷里，有没有【dex 容器的特征】？
   （容器头自洽 / magic / 声明长度与实际长度匹配）
② 有没有谁在加载它？（加载点可定位 ⇒ 它真的在跑）
③ 反过来：作用对象是数据/日志/配置的那一层，直接排除
```

**认错对象的代价**：对"数据加密层"做 dex dump = **整条流程白忙**。

### 交付形态

```text
【加固识别】
命中家族：<族 A>（p1,p2…）｜<族 B>（p3）｜<族 C>（p4）
dex 保护层：<载荷路径>（判据：<容器头/magic/被谁加载>）
其它保护层：<路径>（判据：<作用对象不是 dex>）
下一步：<解哪个载荷>
```

### 一条便宜又有效的习惯：交叉验证

**用两个独立来源算同一件事**（手工看包内文件 / 另跑一个规则库）。
两边都对上 ⇒ 稳；只有一边命中 ⇒ 回头看是哪边看漏了。

> **"我自己算出来的"和"别人独立算出来的"是两个证据**，不是同一个重复。

## 3. 脱壳验收：三种假状态

**dump 最容易骗人的地方：手段成功了，目的失败了。**

| # | 假状态 | 看起来像什么 | 真实含义 |
|---|---|---|---|
| 1 | **桩 dex** | 文件有效、能解析、能被 jadx 打开 | 里面**只有壳的引导类** |
| 2 | **占位 dex** | `.cache/classes*.dex` 名字很像 | **只有 magic、没有内容** ⇒ 那是「内存加载正在发生」的证据 |
| 3 | **同一份反复 dump** | 一堆不同时间点的文件 | 同一个 **sha256** 出现多次 ⇒ **时机根本没变** |

**第 3 条最容易被忽略**：目录里躺着 7 个 dex，看着很勤奋，其实它们是**同一份**。
**看文件数量没有意义，看"内容的多样性"才有意义。**

桩 dex 的真实长相（实测）：

```text
classes.dex      13,868 字节
字符串数         193 个
含有的类名       s.h.e.l.l.{A,C,N,S}        ← 壳自己的引导类
含有的其它标记   libexec
不含有的东西     com.example、SomeActivity、getAESc …
```

## 4. 三条硬判据（缺一不可）

| # | 判据 | 排除什么 |
|---|---|---|
| 1 | **dumped dex 含非桩业务逻辑** | 桩 dex |
| 2 | 抽取壳额外看：**目标方法 `codeItem` 非空** / `invoke` 数量回升 | "文件完整但方法体被抽走" |
| 3 | **能绑回目标包名 + 版本** | "dump 到了别的东西" |

**第 2 条的可数实例**（抽取壳）：

```text
同一个类、同一个文件：
  注入强制类加载之前：  invoke 数量 = 1
  注入之后：            invoke 数量 = 283      ← 可数、可复现、可对比
```

### ★ 一条更本质的判据：能不能回答我的问题

```text
这一堆 dex 里，有没有我这次任务要的那些类？
（目标包名 / 业务入口 / 请求与签名代码 / native 桥引用）
```

**即使一份 dex 完整有效、体积可观，只要里面没有你要的类，对这次任务就是"没拿到"。**
（"拿到 dex"是过程，"知道了什么"才是目的。）

## 5. 抽取壳：按什么触发，以及怎么主动触发

### 5.1 先验伪：排除"是工具读不出来"

**不能再用同一个工具** —— 换一个独立实现的解析器（例：AOSP `dexdump`）。

```bash
dexdump -d classes4.dex | grep -A3 "name.*<init>"
#   insns size : 7 16-bit code units      ← 指令真实存在
```

两个结论同时成立才算清楚：
| 结论 | 证据 |
|---|---|
| 字节码**在** dex 里（不是文件损坏） | 独立解析器能读出指令流 |
| 但它是 **`nop` 骨架**（不是工具问题） | 连独立解析器看到的也是占位代码 |

### 5.2 对照实验：定位触发点（本项目最有价值的一步）

| 类 | 为什么选它 | `nop` | `invoke` |
|---|---|---|---|
| `…s.a`（真实 Application） | **必然被加载** | **0** | **45** |
| `…s.k`（同 dex，无引用） | **必然没被加载** | 558 | 0 |
| 业务类（未被加载） | —— | 1742 | 1 |

⇒ **触发点 = 类加载**（不是按 dex：同 dex 内两种状态并存；
不是按方法首次执行：Application 的 45 个 invoke 不可能都被执行过）。

**附带观察**：已还原的类**连 `.line` 行号都在** ⇒ 壳是把**完整原始字节码**写回去的。

### 5.3 注入点选择判据

| 候选位置 | 评估 |
|---|---|
| `N.<clinit>` | ❌ 太早 —— 真实 `ClassLoader` 还不存在 |
| `instantiateClassLoader` | ⚠️ 混淆严重，patch 风险高 |
| **`instantiateApplication`** | ✅ `p1` 就是真实 `ClassLoader`，且**早于所有业务代码** |

### 5.4 一条必须有的工程细节

```text
对目标类逐个 Class.forName，【每个类单独 try/catch】
```

**为什么决定成败**：批量里只要有一个抛异常且共用一个 try，
**后面全部不执行**；而"哪些类加载失败"**本身也是信息**。

## 6. 一个被加固改造过的 ELF 长什么样（顺带必有）

| 结构 | 谁需要它 | 能不能改坏 |
|---|---|---|
| **程序头表**（`PT_LOAD`/`PT_DYNAMIC`） | ★ **动态链接器** | ❌ 不能 —— 改坏了它自己起不来 |
| **节表**（`.text`/`.symtab`/`.dynsym`） | 链接器、调试器、**分析工具** | ✅ 能 —— 运行时用不到 |

⇒ 加固的常见手法：**破坏节表**（`e_shoff`/`e_shnum` 置坏）。
后果：`readelf --dyn-syms` 报错、`pyelftools.iter_sections()` 报错**或给假数据**。

**正解：只读 loader 必须的那部分。**

```text
ELF 头 → 程序头 → PT_DYNAMIC → DT_SYMTAB / DT_STRTAB / DT_STRSZ / DT_HASH
DT_HASH 里的 nchain 直接等于符号表项数（不用去数节表）
```

**但要把两件事分清楚**：符号表修复解决的是「**工具读不了**」，
不解决「**符号本来就不存在**」（运行时 `RegisterNatives` 绑定的方法，so 里没有 `Java_...` 符号）。
⇒ 那时该做的是**调用它**，不是再修一次符号表。

### 判据：哪些静态数据可信

```text
问：这个结构，运行时（loader）需不需要？
  需要  → 它一定是真的，可以信
  不需要 → 它可能被故意破坏或被填充假数据
```

**并且**：用"没搜到"下结论之前，先拿一个**已知一定存在**的样本验证你的搜索方法 ——
本项目真的翻过车：扫字符串时**连"已知一定被引用"的都扫出 0 命中** ⇒
"没找到"反映的是**方法坏了**，不是目标不存在。

## 7. 可以直接用的验收清单

```text
【加固识别】
[ ] 命中家族全部列出（含路径/文件名）
[ ] 指定了哪一层管 dex，并给出判据（容器头/magic/被谁加载）
[ ] 交叉验证过（两个独立来源）

【脱壳】
[ ] 文件数 > 1 时，先按 sha256 去重（重复 = 时机没变）
[ ] 每个 dex：magic 有效？体积/字符串数量级合理？
[ ] 里面有目标包名吗？有业务入口类吗？
[ ] 抽取壳：目标方法 codeItem 非空吗？invoke 回升了吗？
[ ] 有没有只带 magic 的占位 dex？（那是"加载中"，不是成果）
[ ] 最终：现在的产物能支撑任务的下一步吗？
```

**最后一行才是验收的终点**，前面全是它的支撑。

## 8. 一个完整例子：爱加密（本项目实测，可当对照组）

**样本**：某新闻 App 8.5.1，`classes.dex` 仅 13,868 字节，`assets/ijiami.dat` 22 MB。

识别结果：命中基础/5代/企业版三组，**dex 保护层 = `assets/ijiami.dat`（容器头自洽）+ `libexec*.so`**。

### 三条硬约束（读壳的 `N.<clinit>` 得出，不是试出来的）

```smali
const/4 v0, 0x1
sput-boolean v0, Ls/h/e/l/l/N;->la:Z      # 默认 la = 1
...
if-eqz v0, :cond_8                        # la == 0 → 走 loadLibrary
  # la == 1（默认）：System.load(filesDir + "/libexec.so")   ← 绝对路径
:cond_8
  # ABI 含 "x86" → loadLibrary("exec_x86")，失败回退 ("exec")
```

| # | 约束 | 实证 |
|---|---|---|
| 1 | **绝对路径 `dlopen` 永不走 native bridge** | `dlopen failed: ".../libexec.so" is for EM_AARCH64 (183) instead of EM_X86_64 (62)` |
| 2 | **x86_64 变体不注册 natives** | JNIEnv 函数表钩子：全程无壳的 `RegisterNatives` |
| 3 | **ARM 变体才注册，但 init 崩在 JNI `FindClass`** | 撞翻译层 W^X 墙 |

⇒ 三条同时满足的唯一解：**让进程与引擎都在 x86_64 上** ⇒ **换 ABI + 把 `la` 改成 0**。

> **这三步是"读出来的"，不是"试出来的"。** 读一个 `<clinit>` 花了一小时，
> 省掉了后面"换各种 frida 姿势"的几天。

### 「省掉某步会看到什么」（排错时反着走）

| 省掉哪步 | 症状 |
|---|---|
| 改 `la=0` | 壳走绝对路径加载 ARM 库 ⇒ `EM_AARCH64` 错误 |
| 放 `lib/x86_64/` | `--abi x86_64` 报 `INSTALL_FAILED_NO_MATCHING_ABIS` |
| 装 `_x86` 后缀那两个副本 | `UnsatisfiedLinkError`，**现象和第 1 步没改一样**（最坑） |
| 吞异常 | 进程 2 秒就死，dump 来不及 |
| 强制类加载 | 拿到的 dex 方法体**全是 nop**，看着"成功"其实没用 |
| **不做运行期验收** | 把"延迟检测正在倒计时"当成基线 ⇒ 后面实验可能全无效 |
