## 3. ★ 八条最贵的教训（每条都花了时间）

### ① 「请登录」不是"路走对了"，是网关的通用拒绝 —— **代价 3 天**

当时的判定代码（**看起来毫无问题**）：

```python
verdict = "签名通过（服务端进入业务逻辑）" if "请登录" in txt or '"code":0' in txt else "被拒"
```

**错在哪**：它把通用拒绝读成了"签名过了、路由对了、只差 token"。
而那条路径与那个主机根本是另一套系统。

**正确判据**：**看响应里有没有"只有对的后端才知道的东西"**（如我的真实学期名与 id）。

### ② 把已确认的 P0 降级成"疑似" —— **代价：一天的真实暴露窗口**

**当时的推理**：响应模型里**没有 `studentId`** ⇒ 无法证明归属 ⇒ 降级"疑似"。

**错在**：这是**缺失型判据**（不可证伪 —— 那个接口本来就不下发这个字段）。

**正确判据**：`schoolId=2` ≠ 我的 `schoolId=5` ⇒ **矛盾 ⇒ 确证**。

### ③ 在错的主机上调试一个正确的签名 —— 见 ①

补充标本：另一个域**也回「请登录!」**（该路径只在第三个域存在）。
⇒ **"不是 404"完全不能证明"路由存在"。**

### ④ 枚举一个池子连打 30 次请求 —— **纪律失当**

为枚举打卡点候选池，连续打了约 30 次读接口；第 ~20 次出现**一次非 JSON 返回**（软限流信号）。

**我当时的自我开脱**："这是读接口，没花钱、没改数据" —— **错**。
风控看的是「**这个账号的行为模式像不像人**」，**代价是账号级的**。

**该做的**：先算组合空间 → 写上限 → 分批 + 间隔 → **遇非 JSON 立即停** → 提前告知委托方量级。

### ⑤ 以为"实验无效"，因为响应里没有回显 —— **差点把成功的 PoC 判成失败**

回读时 `trajectory` 为空 ⇒ 我判"服务端没拿到轨迹 ⇒ 实验无效"。
**事实**：服务端用 URL 交付轨迹时**不回显**，但它**确实读了并据此判定**（三项判定全达标）。

⇒ **"没有回显" ≠ "没有读到"。** 回显是展示行为，判定是业务行为。

**连带教训**：脚本里一个**提前 `return`** 差点把证据丢掉 ⇒
**先落盘证据，再下结论。**

### ⑥ 调一个"方向错"的参数 —— **半天**

为避免被判"白噪声"，去调 GPS 噪声的 AR(1) 系数 ρ：`0.047 → 0.071`，自相关几乎没动。

**根因**：相邻点位移 = AR(1) 噪声的**一阶差分**，差分本身是白的。

**正解**：复刻客户端自己的**卡尔曼平滑** ⇒ 自相关 `0.05~0.28 → 0.60~0.91`。

### ⑦ 平滑把"绕去打卡点"的尖峰一起抹平 —— **4/5 号种子打卡点 0/2**

为避免白噪声加了平滑，结果它把目标也吃掉了。
**修法**：把"必打点是否全命中"排到择优函数**第一位**（多目标择优，不能单目标最优）。

### ⑧ 自查规则本身报假警 —— **差点去"修"一个本来就对的东西**

`pace` 自查最初写成"必须等于 `duration ÷ distance`"，对**真实记录**报假警：
记录 `12′07″`，用下发 `distance=0.35` 算出 `12′00″`，差 7 秒。

**根因**：**下发值是四舍五入的（2 位），而 `pace` 用未舍入值算**。反推验证：`12′07″=727s ⇒ 距离≈0.3466 ⇒ 进位即 0.35` ✅

**教训**：**自查规则必须先在真实样本上跑通** —— 真实记录过不了，是**规则**错了。

## 5. 最终发现（摘要）

| 编号 | 内容 | 等级 |
|---|---|---|
| **P0** | `runRecord/detail?id=` **跨校读他人完整 GPS 轨迹**（`schoolId` 2 vs 我的 5） | P0 |
| **P0** | `applyFor/detail?id=` 读他人请假事由 + 附件直链（我 `getList total=0`，却按 id 读到 6 条） | P0 |
| **P0** | `save` 的 `trajectoryUrl` **无来源校验** ⇒ 服务端抓取任意外部 URL 并据此判定，**架空整个官方上传管控**（兼 SSRF 面） | P0 |
| **P1** | 提交时**服务端不重算**客户端自报的里程/时长/配速/步数 | P1 |
| **P1** | 打卡点随机化**不能防绕过**（候选池很小、每次给 2 ⇒ 组合空间极小；覆盖全池的里程显著低于达标线） | P1 |
| P2 | 排行榜全量下发全校 3119 人姓名/头像；教师名册一次下发 435 条 | P2 |
| P2 | `campus/detail`、`fence/detail` 未按学校隔离 | P2 |
| — | 教师端 6 个端点**正确拒绝**学生 token（**负向结论，同样入档**） | — |

### ★ 它有一件事做对了（必须写进报告）

**打卡点是否达标是服务端从轨迹自己重算的，不采信客户端上报的 `checkInNum`**
（实测：上报 `checkInNum=1` 而轨迹不路过 ⇒ 仍判未达标）。
⇒ **防线的方向是对的，问题在"轨迹的来源没有被约束"。**

### 判定语义（交叉验证 + 能预测）

```text
码 10/11 = 打卡点（文案相同，极性在 type）    30 = 里程    40/41 = 配速
status = 1  ⟺  所有项的 type 均为 0
三条独立记录（不同校、不同 status）交叉，零冲突 ⇒ 解出
```

**风险判断（诚实分两层）**：

## 7. 如果重来（三条）

1. **动手前写一行判据**：「我凭什么说这件事成了？如果它是错的，我会看到什么不一样？」
   —— 第 ①②⑤ 三条教训都能被这一行挡住。
2. **不认识的东西先问"谁知道答案"，而不是"我怎么算出来"**：
   主机/密钥/码表/参数/格式，**六次都是"对方愿意说"**，而我第一反应六次都是"自己算"。
3. **先声明请求预算再动手**：「预计打 N 次，上限 M 次，M 次没结果就停下复盘」
   —— 第 ④ 条就不会发生。
