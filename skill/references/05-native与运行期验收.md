# 05 · Native 与运行期验收

> 本文件解决：**动了运行环境之后，怎么知道"它活得好" —— 以及 native 层的地址怎么不搞混。**
> 适用：hook / patch / 注入 / dump 内存之后；或者从日志拿到一个地址要在 IDA 里找它的时候。

---

## 1. 偏移纪律：六种偏移分开记

**同一个位置，在六种语境下是六个不同的数。** 不写清是哪一种，会**错得很安静**。

| # | 名字 | 定义 | 谁给你 |
|---|---|---|---|
| 1 | **file offset** | 文件里的字节偏移 | 文件工具（`strings -t x`、`xxd`） |
| 2 | **image offset / RVA** | 相对映像基址的偏移 | 分析工具默认显示 |
| 3 | **load base** | 库被映射到的虚拟基址 | `/proc/<pid>/maps` |
| 4 | **runtime address** | 运行时绝对虚拟地址 | Frida / logcat / tombstone |
| 5 | **IDA/Ghidra address** | 工具里显示的地址 | 工具（**先确认 rebase 基准**） |
| 6 | **`so!offset`** | "库名 + 相对偏移" | ★ 人的约定，最不容易错 |

### 关系式

```text
runtime address  =  load base  +  image offset          ← 恒成立
file offset      ≈  image offset                        ← ★ 不总成立
```

**第二条那个"约等于"是雷。** 它成立的前提是「文件布局 == 内存布局」，而这不总成立：

| 何时不成立 | 为什么 |
|---|---|
| 段按页对齐、文件里没 padding | 文件比内存"紧" |
| `.bss` 这类"只在内存里"的段 | 文件里没有对应字节 |
| **节表被加固破坏** | 连"文件布局"这份地图都不可信 |
| dump 出来的 so / 内存镜像 | 本来就是按内存布局展开的 |

> **最危险的等式是 `file offset == image offset`** ——
> 它在**大多数普通 so 上碰巧对**，于是你形成习惯，然后在被改造过的 so 上**安静地错**。

### 换算流程（Frida 地址 → IDA）

```text
① 查 maps 拿 load base
② offset = runtime − load base
③ 按 IDA 的 imagebase 换算后再跳
```

⚠️ **"手工砍高位"有时候会成功** —— 那正是危险信号（成功依赖的恰好是那个"约等于"前提）。

### 为什么 `so!offset` 最好

| 好处 | 说明 |
|---|---|
| 自带基准 | 无歧义 |
| **不含绝对地址** | 跨进程/跨重启/跨设备都有效（**ASLR 一变，绝对地址全废**） |
| 可直接换算 | 拿到 load base 就能还原任意形式 |

### 记录规范（照抄）

```text
libtarget.so!0x12345              ← 主记形式
  file offset   = 0x12345         （仅在"文件布局与内存一致"时写）
  image offset  = 0x12345
  load base     = 0x7f…           ← 记当前这次运行的值
  runtime addr  = 0x7f…
  观测于        : PID / 设备 / ABI / 时间
```

**最后一行不能省** —— 它就是"运行时实验必须可复现"的前提。

### 自检

```text
看到我笔记里的 0x12345，能回答吗：
① 这是哪一种偏移？② 哪个库、哪次运行？③ 怎么换算到其它形式？
三条里有一条答不上来 ⇒ 这条记录不可复现。
```

## 2. 运行期验收：通过闪屏 ≠ 成功

### 为什么"闪屏过了"没有信息量

| 失败类型 | 表现 | 会不会被发现 |
|---|---|---|
| **快失败** | 启动 1~2 秒自杀 / 直接崩 | ✅ 容易 |
| **★ 慢失败** | 进首页正常，几十秒后 / 切后台回来 / 下一次请求时才触发 | ❌ **极易被当成成功** |

> **"我进首页了"作为成功判据是零信息量的** ——
> 它有信息量只在一种情况下：**你已经排除了延迟触发**。

### 五类否定项（必须主动查，不能默认成立）

| # | 迹象 | 说明什么 |
|---|---|---|
| 1 | **PID churn**（进程反复重启） | 被检测 → 自杀 → 被重拉，在循环（★ 最隐蔽：你每次看到的都是"能进首页"） |
| 2 | **未被注入的子进程崩** | 主进程看着好，child/service 没拿到补丁 |
| 3 | **ANR** | 主线程被 hook 拖住 |
| 4 | **原生 tombstone** | native 层崩（patch 副作用或检测） |
| 5 | **Java 致命异常** | 层间不一致（hook 改了类型/签名） |

### 时间维度

```text
启动 / 原生保护类工作：计时运行 120–180 秒
```

| 观察窗口 | 能排除什么 |
|---|---|
| 10 秒 | 只能排除"启动即崩" |
| **120–180 秒** | 覆盖延迟检测、异步看门线程、首屏后的网络校验 |

### ★ 重 trace 与稳定 bypass 必须分成两套

| | 重 trace | 稳定 bypass |
|---|---|---|
| 目的 | **看见** | **不改变其他行为**地通过 |
| hook 面 | 可以广 | 必须**窄** |
| 噪声 | 允许 | 必须低 |

**混用的后果**：无法区分"目标被绕过"和"我的 hook 把别的东西改坏了"。

> 更普遍的一句：**测量工具本身不能成为被测量系统的一部分。**

### 状态日志按库/阶段打

```text
❌ "patch done"                     ← 成功了，但哪一层？
✅ "libexec-patch-status patched=6/6 ok=true"
   "libx-patch-status     patched=2/4 ok=false"    ← 一眼看出哪层没打上
```

> 把"成功"从**整体印象**变成**逐层可读状态**；
> 与证据标签同一种思路：**把"没打上"写成明确、可检索的状态。**

### 多进程：补丁集分别下发

```text
主进程        → 完整补丁集
child/service → 只需要它自己那部分的早期 loader 补丁
```

**每个进程有自己的加载链** ⇒ "注入一次全都好"不成立，
而失败的往往是你没看的那个子进程。

## 3. Native 追踪的几个具体判据

| 场景 | 判据 / 做法 |
|---|---|
| **直接 syscall 退出** | syscall-trace 报的 PC 可能落在 `svc` **之后** ⇒ 看 **`pc - 4`**；只 patch **因果性**的致命 `svc` |
| **`pthread_create` 追踪无效** | 退到 **`clone`**；从线程控制结构恢复 **Bionic pthread start-routine** |
| **信号/崩溃点定性** | 先确认那个地址是**函数入口 / 分发块 / 致命辅助 / 混合初始化检查**，**再**决定窄 hook —— 别上来就把分发块 patch 成 `ret` |
| **自解密库** | 看 `dlopen` / `android_dlopen_ext` / 构造函数 / **构造函数返回** / `mprotect` / `memfd_create` / maps 的 **RX↔RWX 过渡** |
| **内存里的可执行区** | 匿名 `RX/RWX`、memfd 名、VMA 名、权限翻转、自解密区间 —— 这些才是 dump 窗口 |
| **从 maps 取数** | **按 maps 给的 base + size 取，不要按猜的文件大小取** |

## 4. Hook 与轮询：时间窗的选择

设目标值存活时间 **T**、观察间隔 **Δ**：

| 手段 | 什么时候能看到 |
|---|---|
| 轮询 | 只在"值存在"与"你在查"重叠时 —— 概率大致与 `T/Δ` 相关 |
| **Hook** | 只要**挂钩点被走到** ⇒ **必定**截住（与 T 无关） |

**判据：先估 T。**

| T | 用什么 |
|---|---|
| 秒级/分钟级 | 轮询够用（简单、侵入小） |
| **T ≈ 0**（写进去立刻被消费/导航/发送） | ★ **必须 Hook** |
| 不确定 | 先测一次、记时间戳 —— 别猜，量一下 |

### 真实标本

官方登录成功后**写完 token 立刻导航走**。500ms 轮询**抢不到**。

**解法有两层，都值得记**：

```javascript
const _set = Storage.prototype.setItem;         // ① 时机：hook 写操作（事发时截住）
Storage.prototype.setItem = function (k, v) {
  if (k === 'ddToken' && v) {
    document.cookie = 'ddTokenMirror=' + encodeURIComponent(v) + ';path=/;max-age=7200';
  }                                            // ② 载体：镜像到更耐久的存储
  return _set.apply(this, arguments);
};
```

> **不是"让 localStorage 活得更久"，而是"换一个能活的载体"。**

**并且要加兜底**（值可能不走你钩的那条路径）：Hook（主）+ 轮询（兜底）+ 事后快照。
**Hook 提高上限，兜底保下限。**

## 5. 明文桥：在加密前后插一个可编辑的中转

⚠️ **证据等级 `static-candidate`（读源码得出，未亲手复现）** —— 记于此是因为模式值得先想清楚。

### 问题形状

| 事实 | 后果 |
|---|---|
| 抓包看到**密文**（pinning / 自定义加密 / 二进制协议） | 改不了业务字段 |
| Frida 能在 `encrypt()` 前 / `decrypt()` 后看到**明文** | 看得见，但没地方"下手改" |
| 直接改**网络层密文** | 签名/完整性对不上 ⇒ 被拒 |

### 模型

```text
App hook 点 → Frida send({kind, id, body, meta}) → Python 控制器
   → 合成一条 Burp item → 人工改 body → 回填（POST /bridge/<kind>/<id>）
   → Frida 用改后的内容替换 arg/return，继续执行
```

**买到的是迭代速度**：改数据从"改脚本→重启→重跑"（分钟级）变成"在 Burp 里改"（秒级）。

### ★ 位置判据（成败在这里）

| 要改 | 插在哪 | 为什么 |
|---|---|---|
| **请求** | **加密/签名之前**（`encrypt` 入参、序列化器出口、body writer） | 改完之后**后面还会自己签** ⇒ 最终报文自洽 |
| **响应** | **解密之后、业务解析之前** | 业务拿到的是你改过的明文 |
| ❌ 别插 | 签名/完整性**算完之后** | 对不上；更糟的是**掩盖了失败原因** |

**判据**：**改完后 App 有没有自己重新计算签名/加密？** 有 ⇒ 位置对。

### 两个前提

- **要求能注入** ⇒ 对"进不去"的场景**完全无效**；
- **并发必须用 ID 关联**（`kind + id`），不能靠线程或顺序。

## 6. 清单

```text
【偏移】
[ ] 每个地址都写清是哪一种偏移？标注了库 / PID / ABI / 时间？
[ ] 涉及 file offset 时，确认过"文件布局 == 内存布局"？
[ ] 跨工具换算后，两个工具指的是同一个函数？

【运行期验收】
[ ] 计时 120–180 秒？
[ ] PID 有没有反复变化？
[ ] 所有子进程都活着、都拿到补丁了？
[ ] 有没有 ANR / 原生 tombstone / Java 致命异常？
[ ] 状态日志是逐库/逐阶段的（patched=n/m）？
[ ] 重 trace 脚本与长期运行脚本是分开的？

【方法选择】
[ ] 目标的存活时间 T 估过吗（决定 Hook 还是轮询）？
[ ] Hook 生效有可观测证据吗（而不是"我觉得钩上了"）？
```
