# 01 · 判据与证据纪律

> 本文件解决一个问题：**这条结论凭什么信？**
> 适用：定判据、贴标签、写"未知/负向"、或者发现自己在被文案/工具分数牵着走的时候。

---

## 1. 证据有两个维度，别只盯一个

| 维度 | 回答 | 什么时候用 |
|---|---|---|
| **形态**（结构） | 这是"观察"还是"推断"？判据有没有信息量？ | **做实验之前** |
| **强度 / 标签**（等级） | 这条结论现在处在哪一级？ | **做实验之后** |

**它们咬合的方式**：判据决定结论**最多能升到哪一级**；标签记录它**现在在哪一级**。
判据选错 ⇒ 标签会一直卡在低级，而你会误以为"证据还不够多"，
于是继续收集**同样没有信息量**的证据。

---

## 2. 三种东西必须分开写

| 类别 | 定义 | 例子 |
|---|---|---|
| **观察** | 可复现的原始输出 | "回读响应里 `schoolId=2`" |
| **推断** | 由观察推出的结论 | "所以这条记录不属于我所在学校" |
| **未知** | 明确不知道的部分 | "`status=3` 的语义未知，需对方确认" |

**为什么必须分开**：
| 混在一起的后果 | 具体表现 |
|---|---|
| 半年后分不清 | 一句"服务端不重算" —— 是观察还是推断？ |
| 无法复核 | 结论变了，不知道哪一步错了 |
| 无法传承 | 下一个人不知道该重新验证什么 |

**"我不知道 X" 是一句有价值的结论** —— 前提是写下来。它直接变成**给对方的问题清单**。

---

## 3. 判据形态阶梯（决定结论的上限）

| 强度 | 形态 | 定义 | 实例 |
|---|---|---|---|
| ❌ **弱** | **缺失型** | "我没看到 X" | "响应里没有 `studentId`" |
| ⚠️ 中 | 单点观察 | 一次观测 | "这条记录 `status=1`" |
| ✅ 强 | **矛盾型** | 与**已知事实**冲突 | "`schoolId=2` ≠ 我的 `5`" |
| ✅ 强 | **必然型** | 逻辑上不可能有别的解释 | "App 不实例化 Application 就跑不起来" |
| ✅ **最强** | **预测型** | 先预测，再拿新样本验证 | "换 8 个随机种子仍然 10/10" |

### 可证伪性自检（一条就够）

> **如果我的假设是错的，我会看到什么不一样？**

| 判据 | 答案是 | 可证伪 |
|---|---|---|
| 响应里有 `studentId` | "**完全一样**（字段本来就不下发）" | ❌ 无信息量 |
| 记录 `schoolId` ≠ 我的 | "如果是我校的，它就该等于 5" | ✅ |

**"完全一样" ⇒ 这个判据立刻丢掉。**

### 为什么"必然型"强

它**不依赖置信度，只依赖逻辑**。构造方法：找一对**必然成立**的样本。

```text
类A（真实 Application）：【必然被加载】→ nop=0,   invoke=45
类B（同 dex、无引用）  ：【必然没被加载】→ nop=558, invoke=0
⇒ 触发点 = 类加载   （不需要置信度：两边都是"必然"）
```

### 为什么"预测型"最强

它排除了"拟合已知样本"：**在见过的样本上一致，什么都不能证明**。
做法永远是：**先自己算，再对答案**。

## 4. 证据置信度标签

### 4.1 native / 运行时侧

| 标签 | 拿到它必须**做过**这件事 |
|---|---|
| `static-candidate` | 在代码/字符串里**看到** |
| `runtime-hit` | 在**运行时**观测到（日志/hook/maps/tombstone） |
| **`causal`** | 做了**前后对照**：只改那一个量，症状随之变化 |
| `bypass-verified` | 一个**窄**改动让目标通过**事先定义好的成功条件** |
| **`disproven`** | 做了同样的对照，**症状没变**（试过且确认无效） |

### 4.2 请求 / 协议侧

| 标签 | 门槛动作 |
|---|---|
| `static-candidate` | 代码里看到 URL/方法/注解 |
| `traffic-observed` | 抓包抓到了 |
| `hook-confirmed` | hook 显示出参数或签名生成 |
| `native-confirmed` | JNI/so 偏移绑到了这条请求 |
| **`replay-verified`** | **用理解的参数重放成功**（服务端接受了） |

### 4.3 为什么是两套

**"证据够不够"是相对于"你要回答的问题"的**：
native 问"这个函数是不是元凶"→ 终点是 `causal`；
请求问"我能复现它吗"→ 终点是 `replay-verified`。

### 4.4 三个用法

**① 报告里每条结论后面挂一个** —— 读者据此自己判断该信多少，而不是笼统信任整份报告。

**② 标签本身就是待办清单**：
停在 `static-candidate` 的条目 = 下一步实验清单。
> **把"我没验"写成一个可检索的状态，而不是藏在语气里。**
> 写"据说/可能/应该"是模糊的；写 `static-candidate` 是明确的。

**③ `disproven` 必须写** —— 它的价值**只对下一个人成立**。

### 4.5 一条纪律：标签不能自我拔高

**"我很有把握"不是等级，"我做过那个动作"才是。**
看代码觉得"肯定是它" ⇒ 还是 `static-candidate`。

⚠️ **注意 `replay-verified` 的边界**：重放是**写操作、有副作用** ⇒
必须授权、必须单发、必须留台账。等级最高的证据往往也是风险最高的动作。

## 5. 文案不是根因

服务端错误提示是**给人看的**，不是给排错用的。
它有一个很坏的设计倾向：**让一切看起来像"差一步就成功"**
（把责任放在用户侧，而不是承认"你访问的东西不存在"）。

### 判据可靠度（从弱到强）

| 判据 | 强度 | 为什么 |
|---|---|---|
| `msg` / 错误文案 | ❌ **最弱** | 可兜底、可覆盖、**无极性** |
| HTTP 状态码 | ⚠️ 中 | 分了几层，也会被统一处理 |
| 顶层 `code` | ⚠️ 中 | 混装了业务/框架/异常三层语义 |
| **只可能是枚举的字段** | ✅ 强 | 枚举值没法被美化，只能被**解释** |
| **行为证据**（它接下来做了什么） | ✅ **最强** | 弹了滑块 = 待校验；返回业务数据 = 到了后端 |

### 真实标本（每一个都把我们带偏过）

| 文案 | 我读成 | 实际 |
|---|---|---|
| `请登录` | "路走对了，只差 token" | **网关通用拒绝**（它不知道路径存不存在）→ **三天** |
| `手机号格式有误` | 参数格式问题 | 风控"这请求不像官方客户端" |
| `满足打卡点要求` | 我达标了 | **固定规则描述**；`10`/`11` 文案一字不差，过没过在 `type` |
| `loginStatus:1` | 登录成功 | **需要人机校验** |

**同一文案、两种结论** —— 这是"文案不能当判据"最干净的证明：

```text
10 → "满足打卡点要求"   type=0   ← 达标
11 → "满足打卡点要求"   type=1   ← 不达标
```

### 该怎么做

**找"翻译字段"**。看到这类成对出现的字段，那是把内部枚举直接交给你了，
比反编译客户端便宜太多：

| 形态 | 含义 |
|---|---|
| `reason` + `reasonFormat` | 判定码表 |
| `status` + `statusText` | 状态机枚举 |
| `errorCode` + `errorMessage` | 错误码表 |

## 6. 工具的分数往往答的不是你的问题

**用一个指标之前，先问它回答的是哪个问题。**

| 你拿到的 | 它在回答 | 你要问的 |
|---|---|---|
| "dex 格式有效，score=30" | 这个文件**坏没坏** | 我**拿到业务代码**了吗 |
| "HTTP 200" | 请求被接住了 | 数据是我要的吗 |
| "`code:0`" | 这一层没报错 | 我要的东西存在吗 |

### 一个实测出来的判据缺口（值得当模板记）

拿一个**全是桩 dex** 的目录（7 个文件、同一 sha256、每个 13,860 字节）喂给某个公开的 dump 校验脚本：

```text
输出：top: T3.00_REAL_….dex   score = 30
      reasons = valid dex magic(+20) / declared size matches(+8)
                / crypto hints:1(+1) / business hints:1(+1)
```

**全是加分项，桩被封成了 top。** 读源码定位根因：

```python
# 它的"壳"关键词表
"shell": StubApp|ShellApplication|ProxyApplication|DexHelper|SecShell|Bangcle|secexe
# 而桩 dex 里实际含：s/h/e/l/l ✅  libexec ✅   ← 两个都不在表里 ⇒ 不扣分
```

而且它的评分里**没有体积项、没有类数项、没有目标包名项**。

> ⇒ 它算的是「**格式良好度 + 关键词密度**」；我要的是「**这是不是真业务代码**」。
> **判据和问题不匹配** —— 这是根因，不是它"坏了"。

**公平地说**：同一个脚本把 `.bin` 里的匿名内存块（scudo 分配区）**正确排除**了。
**能正确否掉"看起来像"的，和能正确认出"真是"的，是两种能力。**

## 7. 先落盘证据，再下结论

**顺序反了，你会在结论错的时候连证据都没了。**

真实事故：回读时发现 `trajectory` 为空，脚本用一个提前 `return` 判断"实验无效" ——
结果连 `status`（真正的判据）都没落盘。
而事实是：**服务端用 URL 交付轨迹时不回显轨迹，但它确实读了并据此判定**。

> **"没有回显" ≠ "没有读到"。**
> 回显是**展示行为**，判定是**业务行为** —— 两者可以完全独立。

**纪律**：在做任何"提前返回 / 提前判定"之前，**先把原始响应落盘**。

## 8. 可以直接抄的写法

### 8.1 证据链表

```markdown
| 环节 | 证据（原始输出/命令） | 文件·函数·偏移 | 标签 |
|---|---|---|---|
| 定址 | 响应含我的真实学期名与 id | school-api `semester/currSemester` | traffic-observed |
| 签名 | 与官方自签样本逐字符一致（2/2） | `RequestParamInterceptor` | causal |
| 排除 | 同样对照法堵 A，症状未变 | —— | disproven |
```

**"证据"那一列不能空** —— 空的那一列会让标签退化成形容词。

### 8.2 未知清单（交给对方回答）

```markdown
| 未知项 | 我的观测 | 谁能回答 |
|---|---|---|
| `status=3` 语义 | 仅见过一次（某记录） | 平台方 |
| 是否触发告警 | 枚举中出现过一次非 JSON | 平台方 |
```

### 8.3 收尾四问

```text
① 每个低级标签，下一步实验是什么？
② 我的"未知"里，哪些其实能用一次对照实验消掉？
③ 有没有结论其实已经够强，但我写成了"疑似"？（别浪费强证据）
④ 有没有结论我写得很确定，但其实只是 static-candidate？（别夸大）
```
